## 一、枚举（Enum）

### 1.1 项目中的使用场景

#### 场景一：RedisKeys 枚举统一管理 Redis 的 key（最典型）

在微服务里，多个服务都会往 Redis 写数据（验证码、登录 token、缓存等），如果 key 的前缀散落在各个业务代码里，很容易写错、重复、或者忘记设过期时间。本项目用一个枚举 `RedisKeys` 统一收口：

```java
@Getter
public enum RedisKeys {

    // 枚举值 --> 因为外界无法创建对象,所以必须调用自己的构造方法先创建枚举对象
    VERIFY_CODE("verify_code:", 60 * 5);

    // key 前缀
    private String prefix;
    // 过期时间
    private long expire;

    // 构造方法私有,外界无法 new
    private RedisKeys(String prefix, long expire) {
        this.prefix = prefix;
        this.expire = expire;
    }

    // 对外提供方法 --> 外界拼接获取key
    public String join(String... values) {
        StringBuffer sb = new StringBuffer();
        sb.append(prefix);
        for (String value : values) {
            sb.append(":");
            sb.append(value);
        }
        return sb.toString();
    }
}
```

业务中两处真实调用：

**① 发送验证码时写入 Redis**（`SmsServiceImpl`）：

```java
public void sendVerifyCode(String phone) {
    String verifyCode = String.format("%04d", new Random().nextInt(10000));
    // 用枚举拼 key：verify_code:13800000000
    String key = RedisKeys.VERIFY_CODE.join(phone);
    // 过期时间也由枚举统一管理：60 * 5 = 300 秒
    redisService.setCacheObject(key, verifyCode,
            RedisKeys.VERIFY_CODE.getExpire(), TimeUnit.SECONDS);
}
```

**② 注册时从 Redis 取出校验**（`PcLoginService#register`）：

```java
String key = RedisKeys.VERIFY_CODE.join(register.getUsername());
String verifyCode = redisService.getCacheObject(key);
if (StringUtils.isEmpty(verifyCode)) {
    throw new ServiceException("手机验证码不存在或者已失效");
}
if (!StringUtils.equals(verifyCode, register.getVerifyCode())) {
    throw new ServiceException("手机验证码错误");
}
```

> 这样做的好处：key 前缀和过期时间集中在一个枚举里管理，后续如果要新增一种缓存（比如登录 token、短信限流），只需加一个枚举值 `LOGIN_TOKEN("login_token:", 1800)`，所有调用点天然保持一致，不会出现 "verify_code:" 和 "verifyCode:" 两种写法并存的问题。

#### 场景二：UserStatus 枚举描述用户状态

登录时需要判断用户是否被删除、是否被停用，本项目用枚举替代魔法值：

```java
public enum UserStatus {
    OK("0", "正常"), DISABLE("1", "停用"), DELETED("2", "删除");

    private final String code;
    private final String info;

    UserStatus(String code, String info) {
        this.code = code;
        this.info = info;
    }
    // getCode / getInfo ...
}
```

在 `SysLoginService` 登录校验中：

```java
if (UserStatus.DELETED.getCode().equals(user.getDelFlag())) {
    throw new ServiceException("对不起，您的账号：" + username + " 已被删除");
}
if (UserStatus.DISABLE.getCode().equals(user.getStatus())) {
    throw new ServiceException("对不起，您的账号：" + username + " 已停用");
}
```

> 好处：相比 `if ("2".equals(user.getDelFlag()))` 这种写法，`UserStatus.DELETED.getCode()` 语义清晰，且把状态码（0/1/2）和中文含义绑定，避免散落的魔法值。

#### 场景三：BusinessType 等枚举配合 @Log 注解记录操作日志

后台管理每个增删改查接口都要记录操作日志，本项目用 `@Log` 注解 + 枚举来标记操作类型：

```java

```

Controller 中的使用：

```java

public R<?> add(@RequestBody Region region) { ... }

```

> AOP 切面拦截带 `@Log` 的方法，根据 `businessType` 字段把 "新增/删除/导出" 等操作类型写入 sys_oper_log 表，便于审计。此外还有 `BusinessStatus`（SUCCESS/FAIL）、`OperatorType`（后台/手机端用户）、`Logical`（权限校验 AND/OR）等枚举，思路一致。

### 1.2 面试可能追问的问题

**Q1：Java 枚举的本质是什么？**
A：Java 枚举本质上是一个继承自 `java.lang.Enum` 的特殊final类。每个枚举常量都是该类的 `public static final` 实例，在类加载的 `<clinit>` 阶段被创建。所以枚举是"单例的集合"，每个枚举值在 JVM 中只有一个实例。

**Q2：为什么枚举构造方法默认是 private？**
A：因为枚举实例只能由 JVM 在类加载时创建（在 static 块中），外部不能 `new`，也不能被继承（final）。这样就保证了枚举值的固定性和唯一性。本项目的 `RedisKeys` 构造方法显式写成 `private`，外部只能通过 `RedisKeys.VERIFY_CODE` 拿到唯一实例。

**Q3：枚举相比常量类（public static final String）有什么优势？**
A：
1. **类型安全**：枚举是独立类型，方法参数声明为 `BusinessType` 就只能传入合法的枚举值，不会传错字符串。
2. **语义丰富**：枚举可以带属性和方法（如 `UserStatus` 同时持有 code 和 info，`RedisKeys` 持有 prefix 和 expire 并提供 join 方法），常量类只能放值。
3. **可遍历**：`values()` 可以枚举所有取值，便于做下拉框、校验。
4. **switch 支持**：编译器会对枚举的 switch 做穷尽性检查。

**Q4：枚举能实现单例模式吗？为什么推荐？**
A：能，而且是最推荐的单例实现方式（Effective Java 推荐）。因为枚举实例的创建由 JVM 在类加载时保证线程安全，且天然防御反射攻击（反射创建枚举会抛 `IllegalArgumentException`）和反序列化破坏（枚举的序列化机制特殊，不会产生新对象）。本项目 `RedisKeys.VERIFY_CODE` 实际就是一个单例。

**Q5：枚举可以用在 switch 中吗？**
A：可以，并且 Java 1.7 起 switch 支持枚举。case 后面直接写枚举常量名（不带类名前缀），编译器会做类型推断和穷尽性检查。

**Q6：枚举可以继承类或被继承吗？**
A：枚举隐式继承 `java.lang.Enum`，由于 Java 单继承，不能再继承别的类；但可以实现接口。枚举类默认是 final 的，不能被继承。如果想让每个枚举值有不同行为，可以让枚举实现接口，或在枚举里定义 abstract 方法，由每个枚举值各自实现（类似策略模式）。

**Q7：枚举的 values() 方法是怎么实现的？**
A：`values()` 是编译器在编译期自动插入的静态方法（不在 Enum 基类里），它返回一个由所有枚举常量组成的新数组（每次调用都 new 新数组，所以修改不会影响内部）。`valueOf(String)` 也是编译器插入的，通过 name 匹配。

## 二、递归（Recursion）

### 2.1 项目中的使用场景

#### 场景一：菜单树构建（SysMenuServiceImpl）

后台菜单是典型的树形结构（一级目录 → 二级菜单 → 三级按钮）。数据库里存的是扁平结构（每个菜单有 `menu_id` 和 `parent_id`），查出来后需要组装成树返回给前端渲染侧边栏。

核心递归方法 `recursionFn`：

```java
/**
 * 递归列表：为某个节点挂载它的子节点，并继续向下递归
 */
private void recursionFn(List<SysMenu> list, SysMenu t) {
    // 1. 找当前节点的所有直接子节点
    List<SysMenu> childList = getChildList(list, t);
    // 2. 挂到 children 属性上
    t.setChildren(childList);
    // 3. 对每个子节点继续递归（如果它还有孩子）
    for (SysMenu tChild : childList) {
        if (hasChild(list, tChild)) {
            recursionFn(list, tChild);
        }
    }
}

/**
 * 从全量列表中挑出 parentId == t.menuId 的节点
 */
private List<SysMenu> getChildList(List<SysMenu> list, SysMenu t) {
    List<SysMenu> tlist = new ArrayList<>();
    for (SysMenu n : list) {
        if (n.getParentId().longValue() == t.getMenuId().longValue()) {
            tlist.add(n);
        }
    }
    return tlist;
}

/**
 * 判断是否有子节点（递归出口辅助方法）
 */
private boolean hasChild(List<SysMenu> list, SysMenu t) {
    return getChildList(list, t).size() > 0;
}
```

入口方法 `getChildPerms` 从 parentId=0 的根节点开始递归：

```java
public List<SysMenu> getChildPerms(List<SysMenu> list, int parentId) {
    List<SysMenu> returnList = new ArrayList<>();
    for (SysMenu t : list) {
        if (t.getParentId() == parentId) {
            recursionFn(list, t);
            returnList.add(t);
        }
    }
    return returnList;
}
```

调用处（`selectMenuTreeByUserId`）：

```java
List<SysMenu> menus = menuMapper.selectMenuTreeByUserId(userId);
return getChildPerms(menus, 0);   // 从根节点开始递归构建树
```

#### 场景二：部门树构建（SysDeptServiceImpl）

部门管理同样是树形结构，逻辑几乎完全一样（recursionFn / getChildList / hasChild 三件套）：

```java
public List<SysDept> buildDeptTree(List<SysDept> depts) {
    List<SysDept> returnList = new ArrayList<>();
    List<Long> tempList = depts.stream().map(SysDept::getDeptId).collect(Collectors.toList());
    for (SysDept dept : depts) {
        // 找出顶级节点（其 parentId 不在当前列表中的就是根）
        if (!tempList.contains(dept.getParentId())) {
            recursionFn(depts, dept);
            returnList.add(dept);
        }
    }
    if (returnList.isEmpty()) {
        returnList = depts;
    }
    return returnList;
}
```

#### 场景三：目的地吐司导航（向上递归找父节点）

与场景一、二的"向下递归找子节点"不同,吐司导航是"**向上递归找父节点**"的典型例子。攻略页面顶部会显示一条面包屑(如 `中国 / 广东 / 广州`),数据库里只存了广州的 `parentId=广东id`,需要沿着 parentId 一路向上找到根,再反序输出。

核心递归方法 `createToast`:

```java
@Override
public List<Destination> queryToastsByDestId(Long destId) {
    // 递归实现
    List<Destination> list = new ArrayList<>();
    createToast(list, destId);
    // 反序输出:递归是从当前节点往上找,结果顺序是 广州→广东→中国,需要反转成 中国→广东→广州
    Collections.reverse(list);
    return list;
}

// 自定义递归方法:从当前节点出发,沿 parentId 向上找
private void createToast(List<Destination> list, Long destId) {
    // 递归出口:destId 为 null,说明已经走到根节点之上,停止
    if (destId == null) {
        return;
    }
    Destination destination = lambdaQuery()
            .eq(Destination::getId, destId)
            .one();
    list.add(destination);  // 把当前节点加入结果
    // 递归调用:继续找它的父节点
    createToast(list, destination.getParentId());
}
```

**与菜单树递归的关键区别**:

| 对比维度 | 菜单树/部门树(场景一、二) | 吐司导航(场景三) |
|---------|------------------------|------------------|
| 递归方向 | 向下找子节点(父→子) | 向上找父节点(子→父) |
| 遍历方式 | 先序遍历,每层可能有多个子节点 | 单链向上,每层只有一个父节点 |
| 数据结构 | 树(N 叉树) | 链表(单链) |
| 递归出口 | 节点没有子节点(hasChild=false) | parentId 为 null(走到根) |
| 结果顺序 | 天然是从根到叶子,无需反转 | 从叶子到根,需要 `Collections.reverse` |
| 查询次数 | 每层查一次 getChildList | 每层查一次当前节点 |

> **面试点**:吐司导航这种"沿父引用向上回溯到根"的递归,本质是链表遍历。因为每层只有一个父节点,所以不会出现菜单树那种 N 叉分支,递归深度就等于节点层级,非常安全。结果反序是常见的技巧 —— 递归天然是"逆序收集"(先处理当前,再处理父级),而业务需要"正序展示"(从根到当前),所以最后 reverse 一次。

> **性能优化**:当前实现每递归一层就查一次数据库,层级深时会有 N 次 SQL。优化方案是一次性把整张目的地表查出来转成 `Map<id, Destination>`,之后查父节点就是内存 O(1) 查询,SQL 次数从 N 降到 1。代码里已注释保留了优化版本。

### 2.2 递归三要素（结合项目讲解）

1. **递归出口（终止条件）**：当前节点没有子节点时停止。本项目通过 `hasChild(list, tChild)` 判断，返回 false 就不再进入下一层 `recursionFn`。
2. **递归体（向下一层）**：`recursionFn(list, tChild)` —— 把子节点当作新的父节点继续处理。
3. **参数收敛（问题规模缩小）**：每递归一层，处理的节点层级就更深一层，子节点集合越来越小，最终必然走到叶子节点退出。

### 2.3 面试可能追问的问题

**Q1：递归和迭代（循环）有什么区别？各自的优缺点？**
A：
- 递归：代码简洁，符合树形/分治问题的思维模型；但每次调用都要压栈，层级深时有栈溢出风险，性能略差。
- 迭代：需要自己维护栈/队列，代码稍繁琐；但没有栈溢出风险，性能更好。
- 本项目菜单/部门树层级通常很浅（3~5 层），用递归可读性最好，是合理选择。如果数据量大、层级深（如百万级评论楼中楼），应改成迭代 + 显式栈。

**Q2：你这个递归会不会有问题？比如性能？栈溢出？**
A：
- **性能**：`getChildList` 每次都要遍历整个 list 找孩子，时间复杂度 O(n)，整体 O(n²)。如果菜单数量大（几百上千），可以先用 `Map<parentId, List<子节点>>` 做一次分组（O(n)），之后查孩子就是 O(1)。
- **栈溢出**：菜单/部门树层级有限，不会触发；但若是任意深度的数据（如组织架构、族谱），应加最大深度限制或改迭代。
- **重复计算**：`hasChild` 内部又调了一次 `getChildList`，相当于每个节点查两次孩子，可优化为只查一次。

**Q3：如何把这段递归改成迭代？**
A：用显式栈或队列。思路：把所有节点按 parentId 分组到 Map 中，然后从根节点入栈，循环出栈、挂载子节点、子节点入栈，直到栈空。这样避免了方法调用栈，可处理任意深度。

**Q4：递归和回溯是一回事吗？递归和回溯有什么区别和联系？**

**一、本质定义**

- **递归(Recursion)** 是一种**执行机制**:方法自己调用自己,把大问题拆成同结构的子问题,直到触底(出口)再逐层返回。它是一种"代码组织方式",关注的是"怎么调用"。
- **回溯(Backtracking)** 是一种**算法思想**:通过"试探 + 撤销"穷举所有可能的解,走不通就回退一步换条路走,核心是"选择、递归、撤销选择"三步曲。它关注的是"怎么搜索解空间"。

**二、联系:回溯通常用递归来实现**

回溯需要维护一条"当前路径",并在失败时回退到上一个分叉点 —— 这种"进入下一层 + 返回上一层"的栈结构,天然适合用递归的方法调用栈来表达。经典回溯模板:

```java
void backtrack(路径, 选择列表) {
    if (满足结束条件) {
        结果.add(路径的拷贝);   // 注意是拷贝,因为路径后面还要撤销
        return;
    }
    for (选择 : 选择列表) {
        做选择;              // 前置:把当前选择加入路径
        backtrack(路径, 选择列表);  // 递归进入下一层
        撤销选择;            // 后置:把当前选择移出路径(回溯的核心!)
    }
}
```

模板里的"撤销选择"就是回溯的精髓 —— 也是它和普通递归最直观的区别。

**三、核心区别对比**

| 维度 | 递归 | 回溯 |
|------|------|------|
| 定位 | 执行机制(代码怎么写) | 算法思想(问题怎么解) |
| 目的 | 把大问题拆成同结构小问题 | 穷举所有可能解,找满足条件的 |
| 是否撤销 | 一般**不撤销**状态,结果在递归过程中累积 | **必须撤销**选择,保证每个分支起点干净 |
| 结果收集 | 通常在出口处 return,或通过副作用累积 | 在叶子节点拷贝当前路径加入结果集 |
| 典型场景 | 树遍历、阶乘、斐波那契、构建树 | 全排列、组合、N 皇后、数独、走迷宫 |
| 复杂度关注点 | 递归深度(栈溢出) | 剪枝(减少搜索空间) |

**四、用项目例子说明区别**

本项目的三个递归场景,**都不是回溯**:

- **菜单树/部门树**:递归向下挂载子节点,一旦挂上就不会撤销,最终所有节点都留在树里。这是"遍历型递归",不是"搜索型回溯"。
- **吐司导航**:沿 parentId 向上找,路径唯一(每个节点只有一个父),不存在"走不通要换条路"的情况,也就不需要撤销。

**对比一个真正的回溯例子**(面试常考):求数组的所有全排列:

```java
// 回溯:每次选一个数加入路径,递归后再撤销,换下一个数选
void permute(int[] nums, List<Integer> path, boolean[] used, List<List<Integer>> res) {
    if (path.size() == nums.length) {
        res.add(new ArrayList<>(path));   // 拷贝路径,因为后面还要撤销
        return;
    }
    for (int i = 0; i < nums.length; i++) {
        if (used[i]) continue;
        path.add(nums[i]);                // ① 做选择
        used[i] = true;
        permute(nums, path, used, res);   // ② 递归进入下一层
        used[i] = false;
        path.remove(path.size() - 1);     // ③ 撤销选择(回溯的核心!)
    }
}
```

注意第 ③ 步:递归返回后必须把刚加入的数移出 path,否则下一个分支的起点就不干净了。这种"撤销"操作在本项目的树构建递归里是**没有**的 —— 因为树构建是"累积型"的,所有节点都要保留;而全排列是"搜索型"的,每条路径只能保留一种选择。

**五、一句话总结**

> 递归是"自己调自己"的执行机制,回溯是"试探+撤销"的搜索思想。回溯通常用递归实现,但递归不一定都是回溯 —— 关键看**有没有"撤销选择"这一步**。本项目构建树/吐司导航是普通递归,不涉及回溯。

**六、易混淆点:后序递归 ≠ 回溯算法**

这是个非常容易被误判的地方。以本项目的吐司导航为例,有两种写法都能得到正确结果,但经常被误认为是"回溯":

**写法一:前序递归(操作在"递"阶段,原版)**

```java
private void createToast(List<Destination> list, Long destId) {
    if (destId == null) return;
    Destination destination = lambdaQuery().eq(Destination::getId, destId).one();
    list.add(destination);                          // ★ 先 add
    createToast(list, destination.getParentId());   // 再递归
}
// 结果: [广州, 广东, 中国]  →  需要 Collections.reverse
```

**写法二:后序递归(操作在"归"阶段,巧妙版)**

```java
private void createToast(List<Destination> list, Long destId) {
    if (destId == null) return;
    Destination destination = lambdaQuery().eq(Destination::getId, destId).one();
    createToast(list, destination.getParentId());   // 先递归到底
    list.add(destination);                          // ★ "归"时才 add
}
// 结果: [中国, 广东, 广州]  →  天然正序,不用 reverse
```

写法二很巧妙,执行流程是"一路递到底(广州→广东→中国→null),再在回返时逐层 add",所以天然得到正序。但它**不是回溯算法**,理由是:

| 判断维度 | 写法二(后序递归) | 真正的回溯算法(如全排列) |
|---------|----------------|----------------------|
| 有没有撤销操作 | ❌ add 之后从不 remove | ✅ 递归返回后必须 remove |
| 是否在搜索解空间 | ❌ 路径唯一,不存在换条路 | ✅ 多个候选选择,逐个试探 |
| "回溯"指什么 | 指"归"阶段(递归返回,自然过程) | 指"撤销选择退回分叉点"(主动操作) |

**关键辨析:"回溯"有两个层面的含义,不能混为一谈**

| 层面 | 含义 | 写法二 |
|------|------|--------|
| 递归执行阶段的"回溯" | 指"归"的过程(递归返回),是递归的自然组成部分 | ✅ 利用了这个阶段 |
| 算法分类的"回溯算法" | 指"试探 + 撤销选择"穷举解空间的算法 | ❌ 没有"撤销"步骤 |

**判断标准(一句话)**:

> 有没有 `remove` / 撤销操作,是判断"回溯算法"的唯一标志。有撤销才是回溯算法,没有就是普通递归(无论前序还是后序)。

**前序 vs 后序递归的本质区别**:

| 维度 | 前序递归 | 后序递归 |
|------|---------|---------|
| 操作位置 | 递归调用**之前** | 递归调用**之后** |
| 处理顺序 | 先处理当前,再处理子/父 | 先处理子/父,再处理当前 |
| 典型对应 | 树的前序遍历、构建树(父先入结果) | 树的后序遍历、计算目录大小(子先算完) |
| 吐司导航结果 | 逆序,需 reverse | 正序,无需 reverse |

> 面试时如果被问"你这个吐司导航能不能用回溯写?",可以回答:吐司导航路径唯一,没有分叉可选,用前序或后序递归即可,不需要回溯。回溯适用于"有多条候选路径需要试探"的场景,如全排列、N 皇后。把"后序递归"误叫成"回溯"是常见错误,核心区别在于有没有"撤销选择"这一步。

**Q5：递归方法的返回值和副作用怎么设计的？**
A：本项目的 `recursionFn` 是 void，通过副作用（`t.setChildren(childList)`）直接修改传入对象的状态，不返回值。这种写法在树构建场景常见，因为树是"原地组装"。如果追求函数式风格，可以改成返回新节点的方式。

**Q6：除了构建树，递归还常用在哪些场景？**
A：文件目录遍历、JSON/XML 解析、JSON 序列化（对象图含嵌套）、分治算法（快排、归并）、回溯算法（全排列、N 皇后）、树的遍历（前/中/后序）、计算斐波那契/阶乘等。

## 三、OSS 对象存储

> 项目背景:文件上传模块(`travel-modules-file`)需要存储用户头像、游记图片等资源。传统本地磁盘存储存在单机容量受限、无法水平扩展、不支持高并发访问等问题,所以项目引入了对象存储服务(OSS)。本项目支持 5 种存储方式切换:本地磁盘 / MinIO / 阿里云 OSS / 七牛云 / FastDFS,通过配置 `store.type` 决定使用哪一种。

### 3.1 什么是对象存储

**对象存储(Object Storage)** 是一种以"对象"为基本单位的分布式存储架构,专门用来存海量非结构化数据(图片、视频、文档等)。与传统文件系统、数据库存储形成对比:

| 存储方式 | 存储单位 | 特点 | 典型场景 |
|---------|---------|------|---------|
| **本地文件系统** | 文件+目录树 | 路径层级深、单机容量受限、无冗余 | 小项目临时存储 |
| **数据库(BLOB)** | 表字段 | 读写慢、占连接、影响业务查询 | 极少用 |
| **对象存储** | 对象(扁平,Key-Value) | 海量扩展、HTTP 直接访问、高可用 | 图片/视频/文档 |

**对象存储的核心概念**:

- **Bucket(桶/存储空间)**:最顶层的容器,类似"文件夹"。每个对象必须属于某个 Bucket。命名全局唯一。
- **Object(对象)**:存储的基本单元,由 **Key(对象名) + Data(数据) + Metadata(元数据)** 组成。Key 类似文件路径,但对象存储是**扁平**的,没有真正的目录层级(目录是通过 Key 前缀模拟的)。
- **Endpoint(接入点)**:访问 OSS 的域名,如 `https://oss-cn-hangzhou.aliyuncs.com`。

### 3.2 为什么不用本地存储而用 OSS

| 维度 | 本地磁盘存储 | 对象存储(OSS) |
|------|------------|--------------|
| 扩展性 | 单机容量上限,加盘要停机 | 近乎无限扩展,按需扩容 |
| 高可用 | 服务器宕机即丢失(除非做 RAID) | 多副本/纠删码,数据可靠性 99.9999999999%(12 个 9) |
| 访问方式 | 需要服务器中转(Nginx 静态映射) | HTTP 直接访问,带 CDN 加速 |
| 跨服务共享 | 微服务间无法直接访问彼此磁盘 | 所有服务通过同一 Endpoint 访问 |
| 成本 | 硬件成本 + 运维 | 按用量付费,小项目几乎免费额度 |

> 本项目微服务架构下,如果用本地存储,文件存到 file 服务的磁盘上,其他服务(member/strategy)要访问就得走 HTTP 再中转一次,效率低且耦合。用 OSS 后,所有服务拿到 URL 就能直接访问,彻底解耦。

### 3.3 项目支持的 5 种存储方案对比

本项目通过 `store.type` 配置切换:

| 方案 | havingValue | 类型 | 说明 |
|------|------------|------|------|
| 本地磁盘 | `local` | 自建 | 存到服务器本地磁盘 + Spring 静态资源映射 |
| MinIO | `minio` | 自建 | 开源对象存储,可私有化部署,兼容 S3 协议 |
| 阿里云 OSS | `alioss` | 公有云 | 阿里云提供的对象存储服务 |
| 七牛云 | `qiniu` | 公有云 | 七牛云对象存储(Kodo) |
| FastDFS | `fdfs` | 自建 | 早期开源分布式文件系统 |

#### 方案一:MinIO(项目主推)

MinIO 是开源的对象存储,兼容 Amazon S3 API,适合**私有化部署**(自己搭服务器,数据不出内网)。本项目 `MinioSysFileServiceImpl` 的上传流程:

```java
@Override
public String uploadFile(MultipartFile file) throws Exception {
    String fileName = FileUploadUtils.extractFilename(file);
    InputStream inputStream = file.getInputStream();
    PutObjectArgs args = PutObjectArgs.builder()
            .bucket(minioConfig.getBucketName())   // 桶名
            .object(fileName)                      // 对象 Key
            .stream(inputStream, file.getSize(), -1)
            .contentType(file.getContentType())
            .build();
    client.putObject(args);                        // 上传到 MinIO
    return minioConfig.getUrl() + "/" + minioConfig.getBucketName() + "/" + fileName;
}
```

配套配置类 `MinioConfig`,用 `@ConfigurationProperties(prefix="minio")` 绑定连接参数,并 `@Bean` 创建 `MinioClient`:

```java
@Configuration
@ConfigurationProperties(prefix = "minio")
public class MinioConfig {
    private String url;        // 服务地址,如 http://127.0.0.1:9000
    private String accessKey;  // 账号
    private String secretKey;  // 密码
    private String bucketName; // 桶名

    @Bean
    public MinioClient getMinioClient() {
        return MinioClient.builder()
                .endpoint(url)
                .credentials(accessKey, secretKey)
                .build();
    }
}
```

nacos 配置示例:
```yaml
store:
  type: minio          # 切换存储方式
minio:
  url: http://127.0.0.1:9000
  access-key: minioadmin
  secret-key: minioadmin
  bucket-name: wolf2w
```

#### 方案二:阿里云 OSS

阿里云提供的公有云对象存储,数据存在阿里云机房,按用量付费。`AliOssSysFileServiceImpl` 的特点是**每次上传都 new 一个 OSSClient,用完 shutdown**(与 MinIO 的单例 client 不同):

```java
@Override
public String uploadFile(MultipartFile file) throws Exception {
    String fileName = UUID.randomUUID() + "." + FilenameUtils.getExtension(file.getOriginalFilename());
    // 每次创建客户端(适合低频上传场景;高频应复用)
    OSS ossClient = new OSSClientBuilder().build(endpoint, accessKeyId, accessKeySecret);
    try {
        PutObjectRequest request = new PutObjectRequest(bucketName, fileName, file.getInputStream());
        ossClient.putObject(request);
        return url + fileName;
    } finally {
        ossClient.shutdown();   // 必须关闭,否则连接泄漏
    }
}
```

#### 方案三:七牛云

与阿里云 OSS 类似,也是公有云存储,SDK 不同。上传需要先用 AccessKey/SecretKey 生成 `upToken`(上传凭证),再用 `UploadManager.put` 上传:

```java
Auth auth = Auth.create(accessKey, secretKey);
String upToken = auth.uploadToken(bucket);
Response response = uploadManager.put(file.getInputStream(), key, upToken, null, null);
```

> 七牛云对个人开发者有免费额度(10GB 存储 + 10GB/月 流量),适合学习项目。

#### 方案四:FastDFS

FastDFS 是早期开源的分布式文件系统(C 语言编写),架构上分 Tracker(调度)和 Storage(存储)两组节点。本项目用 `tobato` 开源客户端:

```java
StorePath storePath = storageClient.uploadFile(inputStream, file.getSize(),
        FileTypeUtils.getExtension(file), null);
return domain + "/" + storePath.getFullPath();   // group1/M00/00/00/xxx.jpg
```

> FastDFS 返回的 URL 带 `group` 前缀(如 `group1/M00/...`),这是它独有的分组机制。现在新项目更倾向用 MinIO,FastDFS 逐渐被淘汰。

#### 方案五:本地磁盘(兜底方案)

存到服务器本地磁盘,用 Spring 的 `ResourceHandlerRegistry` 做 URL 到文件路径的映射:

```java
// LocalSysFileServiceImpl
String name = FileUploadUtils.upload(localFilePath, file);
String url = domain + localFilePrefix + name;   // http://localhost:9300/static/xxx.jpg

// ResourcesConfig 做静态资源映射
registry.addResourceHandler(localFilePrefix + "/**")
        .addResourceLocations("file:" + localFilePath + File.separator);
```

> 本地存储还带了 `@Primary` 注解,作为兜底首选实现(详见下一节策略模式)。

### 3.4 面试可能追问的问题

**Q1:为什么要用对象存储,不用本地文件系统?**
A:本地文件系统在微服务架构下有三个硬伤:① 单机容量有限,扩展要停机加盘;② 服务间无法直接访问彼此磁盘,必须 HTTP 中转,耦合且低效;③ 没有多副本,服务器宕机数据丢失。对象存储提供 HTTP 直接访问、近乎无限扩展、多副本高可用,微服务拿到 URL 就能共享访问。本项目 file 服务专门做上传,其他服务(member/strategy)只存 URL,彻底解耦。

**Q2:MinIO 和阿里云 OSS 有什么区别?怎么选?**
A:
- **部署方式**:MinIO 是开源的,自己搭服务器私有化部署,数据在内网;OSS 是阿里云托管的,数据在阿里云机房。
- **成本**:MinIO 硬件成本一次性投入,数据量大时便宜;OSS 按用量付费,小项目有免费额度,量大时贵。
- **协议**:MinIO 兼容 S3 API,OSS 是自家协议(也兼容 S3)。
- **选择**:对数据安全要求高、有运维能力的公司选 MinIO;创业公司/个人项目图省事选 OSS。本项目两种都支持,通过配置切换。

**Q3:MinIO 的 Bucket 和 Object 是什么关系?**
A:Bucket 是最顶层的容器,Object 是存储在 Bucket 里的对象。一个 Bucket 可以存无数个 Object,每个 Object 有唯一的 Key(类似文件路径)。访问 URL 的格式是 `endpoint/bucket/key`,如 `http://127.0.0.1:9000/wolf2w/2026/08/11/xxx.jpg`。Bucket 命名全局唯一,创建后不能改名。

**Q4:上传文件时,文件名怎么生成?为什么要重命名?**
A:本项目用 `FileUploadUtils.extractFilename(file)` 生成基于日期目录 + UUID 的文件名(如 `2026/08/11/uuid.jpg`),原因有三:① 避免同名文件覆盖(用户都传 "avatar.jpg" 会冲突);② UUID 防止猜测 URL 恶意访问;③ 日期目录方便管理和清理。阿里云实现里用的是 `UUID.randomUUID() + 扩展名`,思路一致。

**Q5:OSS 上传大文件(如 1GB 视频)怎么处理?**
A:大文件不能一次性上传(内存扛不住、网络中断要重传),用**分片上传**(Multipart Upload):① 客户端把文件切成多个小片(如 5MB 一片);② 并发上传各片,OSS 端暂存;③ 全部上传完调 CompleteMultipartUpload 合并。MinIO/OSS SDK 都提供了 `uploadObject` 的分片版本。本项目只演示了普通上传,生产环境传大文件应改用分片。

**Q6:对象存储是扁平的,怎么实现"目录"效果?**
A:对象存储**没有真正的目录**,目录是通过 Key 的前缀模拟的。比如 Key 是 `2026/08/11/xxx.jpg`,OSS 控制台会显示成 `2026 > 08 > 11 > xxx.jpg` 的层级,但底层其实就是个扁平的 Key。这样设计的好处是 Key 查找是 O(1) 的哈希查找,不像文件系统要逐级遍历目录。

**Q7:文件上传的安全性怎么保证?**
A:
1. **鉴权**:AccessKey/SecretKey 不暴露在前端,上传请求走后端 file 服务中转。
2. **文件名校验**:重命名为 UUID,防止路径穿越攻击(如 `../../etc/passwd`)。
3. **类型校验**:`FileUploadUtils` 校验扩展名和 contentType,防止上传 .exe 等可执行文件。
4. **大小限制**:Spring 配置 `spring.servlet.multipart.max-file-size` 限制单文件大小。
5. **私有 Bucket**:敏感数据用私有 Bucket,访问时生成带签名的临时 URL(预签名 URL),过期失效。

**Q8:FastDFS 为什么逐渐被 MinIO 淘汰?**
A:
1. **协议**:FastDFS 是私有协议,生态封闭;MinIO 兼容 S3 协议,生态丰富(各种工具、SDK 通用)。
2. **部署**:FastDFS 要装 Tracker + Storage 两组服务,部署复杂;MinIO 单一二进制,开箱即用。
3. **运维**:FastDFS 是 C 语言写的,二次开发难;MinIO 是 Go 写的,跨平台易维护。
4. **功能**:MinIO 支持版本控制、生命周期管理、Lambda 计算,FastDFS 功能单一。
所以新项目基本都选 MinIO,FastDFS 多见于老项目。

## 四、策略模式 + @ConditionalOnProperty 实现多态切换

> 项目背景:文件上传模块(`travel-modules-file`)需要支持 5 种存储方式切换 —— 本地磁盘 / MinIO / 阿里云 OSS / 七牛云 / FastDFS。如果用 if-else 硬编码,每加一种存储就要改业务代码,违反开闭原则。本项目用 **接口多实现 + `@ConditionalOnProperty` 条件装配** 实现了运行时多态切换,调用方零感知。

### 4.1 整体架构图

```
┌─────────────────────────────────────────────────────────┐
│  SysFileController                                       │
│  @Autowired ISysFileService sysFileService  ← 按类型注入 │
│         ↑ 接口调用                                       │
└─────────┼───────────────────────────────────────────────┘
          │ ISysFileService.uploadFile()  ← 抽象方法
┌─────────┴───────────────────────────────────────────────┐
│                                                         │
│  LocalSysFileServiceImpl   @ConditionalOnProperty(local)│
│  MinioSysFileServiceImpl   @ConditionalOnProperty(minio)│
│  AliOssSysFileServiceImpl  @ConditionalOnProperty(alioss)│
│  QinuSysFileServiceImpl     @ConditionalOnProperty(qiniu)│
│  FastDfsSysFileServiceImpl @ConditionalOnProperty(fdfs) │
│                                                         │
└─────────────────────────────────────────────────────────┘
                          ↑
                  只有一个会被实例化
                  取决于配置文件 store.type
```

### 4.2 核心实现

#### 第一步:定义统一接口(抽象契约)

`ISysFileService` 规定所有存储方式都必须实现"传 MultipartFile,返回访问 URL"的方法:

```java
public interface ISysFileService {
    public String uploadFile(MultipartFile file) throws Exception;
}
```

> 这是多态的基础 —— 调用方永远只面向接口编程,不感知具体实现类。

#### 第二步:每个存储方式写一个实现类 + 条件注解

5 个实现类都实现同一接口,类上标 `@ConditionalOnProperty` 做条件筛选:

| 实现类 | havingValue | 底层技术 |
|--------|------------|---------|
| LocalSysFileServiceImpl | `local` | 本地磁盘 + Spring 资源映射 |
| MinioSysFileServiceImpl | `minio` | MinIO 对象存储 SDK |
| AliOssSysFileServiceImpl | `alioss` | 阿里云 OSS SDK |
| QinuSysFileServiceImpl | `qiniu` | 七牛云 SDK |
| FastDfsSysFileServiceImpl | `fdfs` | FastDFS Java 客户端 |

以本地实现为例:

```java
@Service
@ConditionalOnProperty(prefix = "store", name = "type", havingValue = "local")
public class LocalSysFileServiceImpl implements ISysFileService {

    @Value("${file.prefix}")
    public String localFilePrefix;

    @Value("${file.domain}")
    public String domain;

    @Value("${file.path}")
    private String localFilePath;

    @Override
    public String uploadFile(MultipartFile file) throws Exception {
        String name = FileUploadUtils.upload(localFilePath, file);
        String url = domain + localFilePrefix + name;
        return url;
    }
}
```

#### 第三步:Spring 启动时按配置注册 Bean

`@ConditionalOnProperty` 底层走的是 `@Conditional` + `OnPropertyCondition` 匹配器,匹配逻辑:

```
读取配置项 store.type = xxx
            │
            ▼
┌── 遍历 5 个 Service 实现类 ──────────────────────┐
│  havingValue == "local"   → 匹配?  ✅ 注册 Bean  │
│  havingValue == "minio"   → 匹配?  ❌ 跳过       │
│  havingValue == "alioss"  → 匹配?  ❌ 跳过       │
│  havingValue == "qiniu"   → 匹配?  ❌ 跳过       │
│  havingValue == "fdfs"    → 匹配?  ❌ 跳过       │
└──────────────────────────────────────────────────┘
            │
            ▼
Spring 容器里只有 1 个 ISysFileService Bean
```

注解参数解读:

```java
@ConditionalOnProperty(
    prefix = "store",       // 配置前缀
    name   = "type",        // 属性名,最终匹配 store.type
    havingValue = "minio"   // 当配置值等于此字符串时,才注册 Bean
)
```

关键行为:

| 场景 | 行为 |
|------|------|
| `store.type=minio` | 只有 MinioSysFileServiceImpl 实例化 |
| `store.type=local` | 只有 LocalSysFileServiceImpl 实例化 |
| 配置不存在 | 5 个都不实例化,启动报 `NoSuchBeanDefinitionException` |
| 配置值写错 | 同上,全部跳过,找不到 Bean |

> 注:如果想配置缺失时有兜底方案,可以加 `matchIfMissing = true`,但本项目没加,配置必须明确写。

#### 第四步:Controller 面向接口注入,零 if-else

```java
@RestController
public class SysFileController {

    @Autowired
    private ISysFileService sysFileService;   // 接口类型注入!

    @PostMapping("upload")
    public R<SysFile> upload(MultipartFile file) {
        // 直接调接口方法,JVM 通过虚方法表分派到具体实现
        String url = sysFileService.uploadFile(file);
        SysFile sysFile = new SysFile();
        sysFile.setName(FileUtils.getName(url));
        sysFile.setUrl(url);
        return R.ok(sysFile);
    }
}
```

**这就是多态的精髓** —— 调用方完全不感知具体实现类,只跟接口打交道。切换存储方案时:
1. Controller 一行代码不用改
2. Service 实现类也不用改
3. 只需改配置文件里的 `store.type` 即可

#### 对比不用多态的写法(反模式)

```java
// ❌ 糟糕:调用方写死 if-else,每加一种存储都要改这段代码
@Value("${store.type}")
private String storeType;

public String upload(MultipartFile file) {
    if ("local".equals(storeType)) {
        return localService.uploadFile(file);
    } else if ("minio".equals(storeType)) {
        return minioService.uploadFile(file);
    } else if ("alioss".equals(storeType)) {
        return aliOssService.uploadFile(file);
    } ... // 每加一种都要加 else if
}
```

> 用 `@ConditionalOnProperty` + 接口多实现 + `@Autowired` 接口注入,本质上就是把"运行时 if-else 分支"搬到了"Spring 启动时的 Bean 注册阶段",既做到了策略切换灵活,又保持了调用代码的简洁。

### 4.3 两层条件装配:Service + 配套 Config

`@ConditionalOnProperty` 不只用在 Service 层,项目还通过配置类自动绑定做了第二层的条件化准备。以 MinIO 为例:

- `MinioConfig` 用 `@ConfigurationProperties(prefix="minio")` 绑定连接参数
- 同时 `@Bean` 方法实例化 `MinioClient`(SDK 客户端)
- `MinioSysFileServiceImpl` 里直接 `@Autowired private MinioClient client`

```
store.type = minio
    │
    ├─ MinioConfig 被扫描到(@ConfigurationProperties,无条件,但值可以为 null)
    │   └─ MinioClient Bean 注册
    │
    └─ MinioSysFileServiceImpl 条件匹配成功
        ├─ @Autowired MinioConfig minioConfig (取参数)
        └─ @Autowired MinioClient client    (用 SDK 客户端上传)
```

> 这里 MinioConfig/AliOssConfig/QiniuConfig 本身没有加 `@ConditionalOnProperty`,所以不管 `store.type` 设什么,它们都会被 Spring 加载(只是值可能用不到)。如果想追求极致,可以给 Config 也加同一条 `@ConditionalOnProperty`,避免无用配置类实例化。

### 4.4 @Primary 的配合细节(防御性设计)

`LocalSysFileServiceImpl` 上除了条件注解,还有一个 `@Primary`:

```java
@Service
@ConditionalOnProperty(prefix = "store", name = "type", havingValue = "local")
@Primary   // ← 注意这个
public class LocalSysFileServiceImpl implements ISysFileService
```

**作用**:如果由于某种原因(比如别人新写了一个实现类没加 `@ConditionalOnProperty`),容器里出现了多个 `ISysFileService` Bean,Spring 会优先选带 `@Primary` 的本地实现兜底,而不是直接抛 `NoUniqueBeanDefinitionException`。这是一个防御性设计。

> `@ConditionalOnProperty` 保证"只注册一个",`@Primary` 保证"万一有多个时的首选",两者配合是双重保险。

### 4.5 面试答题模板(结合项目)

> **面试官问:在项目里你是怎么用多态的?/怎么根据配置切换实现?**

**答:** 我项目里文件上传模块做了 5 种存储方式的切换(本地/MinIO/阿里云 OSS/七牛云/FastDFS),用的是 **接口 + 多实现类 + `@ConditionalOnProperty` 条件装配** 的方案。

**第一步:定义统一接口** `ISysFileService`,规定 `uploadFile(MultipartFile)` 方法,所有存储都遵守这个契约。这样调用方(Controller)永远只面对接口编程。

**第二步:每个存储方式写一个实现类**,实现同一接口,然后在类上标 `@ConditionalOnProperty(prefix="store", name="type", havingValue="具体类型")`,比如 MinIO 实现就写 `havingValue="minio"`。

**第三步:Spring 启动时会读配置文件的 `store.type`**,匹配哪个 havingValue,就只实例化哪个 Service Bean 注册到容器里,其他 4 个全部跳过不加载。

**第四步:Controller 直接 `@Autowired ISysFileService` 注入**。因为容器里永远只有 1 个 Bean,所以不会报多 Bean 冲突,调用 `uploadFile()` 时 JVM 会通过虚方法表分派到具体实现类,这就是运行时多态。

**它的好处是**:切换存储方案时,Controller 和业务代码一行都不用改,只改配置文件里的 `store.type` 即可;新增一种存储(比如腾讯云 COS),只需要新增一个实现类加注解,完全符合开闭原则。这比写一堆 if-else 判断存储类型的方案优雅太多。

### 4.6 面试可能追问的问题

**Q1:@ConditionalOnProperty 的作用是什么?底层怎么实现的?**
A:它是 Spring Boot 提供的条件装配注解,根据配置文件中的属性值决定是否注册 Bean。底层走的是 `@Conditional` 机制,匹配器是 `OnPropertyCondition`,在 Spring 容器启动注册 Bean 定义阶段触发:读取 `prefix.name` 对应的配置值,跟 `havingValue` 比较,相等才让该 Bean 定义通过,否则直接跳过,该类不会被实例化。

**Q2:@ConditionalOnProperty 和 @Profile 有什么区别?**
A:
- `@Profile` 按**环境**切换(dev/test/prod),粒度粗,一个环境通常只激活一套配置。
- `@ConditionalOnProperty` 按**任意配置项**切换,粒度细,可以在同一环境里通过多个配置项组合控制多组 Bean 的加载。本项目 5 种存储方式在同一环境里通过 `store.type` 切换,用 `@Profile` 就不合适。

**Q3:如果配置项没写,会怎样?怎么兜底?**
A:默认情况下配置项不存在时,`@ConditionalOnProperty` 匹配失败,Bean 不会被注册,启动时会报 `NoSuchBeanDefinitionException`。兜底方案有两种:
1. 加 `matchIfMissing = true`,让配置缺失时默认匹配成功(适合做兜底实现)。
2. 给某个实现类同时加 `@Primary` + `matchIfMissing = true`,作为默认实现。

**Q4:多个实现类都没加条件注解,Autowired 注入接口会怎样?**
A:Spring 会报 `NoUniqueBeanDefinitionException`,因为找到多个候选 Bean 无法决定注入哪个。解决方法:@Primary 指定首选、@Qualifier 按名字指定、或者用条件注解保证只有一个被注册。本项目用 `@ConditionalOnProperty` 保证唯一,同时 `LocalSysFileServiceImpl` 加 `@Primary` 做双重保险。

**Q5:这种方案和策略模式有什么关系?**
A:这就是策略模式的 Spring 实现版。经典策略模式是:接口 + 多个实现类 + 一个 Context 持有引用 + 客户端手动选择策略。Spring 版把"手动选择"换成了"容器根据配置自动选择",Context 就是 Spring 容器本身,客户端只需 `@Autowired` 接口。优点是更解耦,缺点是策略切换需要重启(因为是启动时注册),不能运行时动态切换。

**Q6:能运行时动态切换存储方式吗?**
A:用 `@ConditionalOnProperty` 不行,因为它是启动时决定 Bean 注册的。如果需要运行时动态切换,可以用:① `@Autowired Map<String, ISysFileService>` 注入所有实现,按 key 动态选;② 自己维护一个策略 Map,根据配置实时路由;③ 用 Spring Event 监听配置变更热替换 Bean(复杂)。但文件存储一般不需要频繁切换,启动时固定一种就够用了。

**Q7:这和 Spring Cloud 的自动装配(spring.factories / AutoConfiguration.imports)有什么区别?**
A:
- `@ConditionalOnProperty` 是**在已被扫描到的类**上加条件,决定要不要实例化。
- `AutoConfiguration.imports` 是解决**类本身都没被扫描到**的问题,把外部 jar 里的配置类引入容器,通常会再配合 `@ConditionalOnProperty` 做条件装配。
- 本项目的 5 个 Service 在本模块内,能被扫描到,所以只用 `@ConditionalOnProperty` 就够了;如果是做成独立 starter 给别人用,就需要配合 `AutoConfiguration.imports`。

### 5.2 表结构设计 —— 大字段分离

**三张表**：

| 表 | 实体 | 说明 |
|----|------|------|
| `ta_note` | Note.java | 游记主表（标题/概要/封面/旅游时间/花费/天数/统计字段） |
| `ta_note_content` | NoteContent.java | 游记富文本内容（大字段独立存储，id 与 note.id 1:1） |
| `ta_note_comment` | NoteComment.java | 游记评论（关联用户信息，冗余 noteTitle） |

**大字段分离的核心代码**：

```java
// NoteContent: id 非自增，与 ta_note.id 保持 1:1
@TableName("ta_note_content")
public class NoteContent {
    @TableId                    // 非自增！
    private Long id;            // 与 ta_note.id 一致
    private String content;     // 富文本 HTML，可能几十 KB
}
```

**为什么这么设计？**

| 对比 | 存一张表 | 大字段分离 |
|------|---------|-----------|
| 列表查询性能 | 全表扫描加载富文本，慢 | 只查主表，不碰大字段 |
| 索引效率 | 大字段占空间，索引页可用的行数少 | 主表紧凑，索引效率高 |
| 更新灵活性 | 修改标题也会锁住大字段行 | 互不影响 |
| 缓存策略 | 做不到差异化 | 主表可全量缓存，内容按需加载 |

> 本项目 Strategy 模块的 `StrategyContent` 也是同样思路。面试时可以说：**“主表存高频查询字段，大字段独立存储，避免全表扫描时加载大文本影响性能”**。

### 5.3 分页查询 —— 多条件动态筛选

`NoteServiceImpl.queryPage` 是本模块最核心的查询方法，通过 `LambdaQueryWrapper` 动态拼条件：

```java
public IPage<Note> queryPage(NoteQuery qo) {
    IPage<Note> page = new Page<>(qo.getCurrentPage(), qo.getPageSize());
    LambdaQueryWrapper<Note> wrapper = new LambdaQueryWrapper<>();

    // 1. 前后台分离：admin=true 不过滤 is_public，可查草稿/待审核
    if (!Boolean.TRUE.equals(qo.getAdmin())) {
        wrapper.in(Note::getIsPublic, "1", "true");  // 兼容历史数据
    }

    // 2. 目的地筛选
    if (qo.getDestId() != null) {
        wrapper.eq(Note::getDestId, qo.getDestId());
    }

    // 3. 出发时间段筛选（1-6 → 1-2月、3-4月...）
    //    MONTH(travel_time) BETWEEN {0} AND {1}
    if (qo.getTravelTimeType() != null) {
        wrapper.apply("MONTH(travel_time) BETWEEN {0} AND {1}", monthStart, monthEnd);
    }

    // 4. 人均花费筛选（1:1-999 / 2:1K-6K / 3:6K-20K / 4:20K+）
    if (qo.getConsumeType() != null) {
        wrapper.between(Note::getAvgConsume, min, max);
    }

    // 5. 排序：viewnum 最热 / create_time 最新
    if ("viewnum".equals(qo.getOrderBy())) {
        wrapper.orderByDesc(Note::getViewnum);
    } else {
        wrapper.orderByDesc(Note::getCreateTime);
    }
    return page(page, wrapper);
}
```

**涉及的知识点**：

| 知识点 | 代码体现 |
|--------|---------|
| **前后台分离查询** | `admin` 标识控制 `is_public` 过滤 |
| **兼容历史数据** | `wrapper.in(isPublic, "1", "true")` |
| **MySQL 函数查询** | `MONTH(travel_time) BETWEEN` |
| **动态排序** | 前端传 `orderBy` 切换排序字段 |
| **Lambda 安全引用** | `Note::getDestId` 避免字段名拼写错误 |

### 5.4 游记详情 —— 微服务数据聚合 + 降级兜底

`NoteServiceImpl.detail` 是典型的微服务数据聚合场景，聚合了 4 个数据源：

```
detail(id)
  ├─ 1. 查 Note 主表（本服务 DB）
  ├─ 2. BeanUtils.copyProperties(note, vo) → 自动拷贝 20+ 字段
  ├─ 3. 查 NoteContent 表 → 富文本内容（本服务 DB）
  ├─ 4. Feign 调 member 服务 → 作者信息（跨服务 RPC）
  │      └─ 失败降级：用 Note 冗余字段兜底
  ├─ 5. person 数字 → 中文映射（1→亲子出游, 2→情侣出行...）
  └─ 6. favorFlag / isFollow 默认 false
```

**VO 继承式设计 —— 不扁平展开**：

```java
// 继承 Note，只补 VO 特有字段，不用手写 20+ 个 setXxx()
public class NoteDetailVO extends Note {
    private NoteContent content;   // 富文本
    private UserInfo author;       // 作者信息
    private Integer day;           // 前端模板别名
    private String personDisplay;  // 中文映射
    private Boolean favorFlag;     // 收藏状态
    private Boolean isFollow;      // 关注状态
}

// 使用：自动拷贝 20+ 基础字段
NoteDetailVO vo = new NoteDetailVO();
BeanUtils.copyProperties(note, vo);  // 一行代码替代 20+ 行 setXxx()
```

**Feign 调用的降级策略（容错设计）**：

```java
// 尝试调 member 服务查作者
try {
    R<UserInfo> r = remoteUserInfoService.getOne(note.getAuthorId(), "inner");
    if (r != null && r.getCode() == R.SUCCESS) {
        vo.setAuthor(r.getData());
    }
} catch (Exception ignored) {
    // member 服务挂了，静默降级
}

// 降级兜底：用 Note 冗余字段
if (vo.getAuthor() == null) {
    UserInfo fallback = new UserInfo();
    fallback.setNickname(note.getAuthorNickname() != null
            ? note.getAuthorNickname() : "匿名用户");
    fallback.setHeadImgUrl(note.getAuthorHeadImgUrl());
    vo.setAuthor(fallback);
}
```

> **核心思想**：即使 member 服务挂了，游记详情页仍能正常展示，只是作者信息用冗余字段兜底，不会直接 500。这是微服务架构中典型的**服务降级**模式。

### 5.5 评论系统 —— 多表关联 + 计数联动

发表评论时做三件事，保证数据一致性：

```java
public void addContent(NoteComment comment) {
    // 1. 设置当前登录用户
    Long userId = SecurityUtils.getUserId();
    comment.setUserId(userId);
    comment.setCreateTime(new Date());
    comment.setStatus("0");

    // 2. 冗余存储游记标题（避免列表页跨表 JOIN）
    Note note = noteService.getById(comment.getNoteId());
    if (note != null) {
        comment.setNoteTitle(note.getTitle());
    }
    baseMapper.insert(comment);

    // 3. 更新游记回复数（SQL 原子操作，避免并发问题）
    noteService.lambdaUpdate()
            .eq(Note::getId, comment.getNoteId())
            .setSql("replynum = replynum + 1")   // ★ SQL 原子操作
            .update();
}
```

**为什么用 `setSql("replynum = replynum + 1")` 而不是 "先查后更新"？**

```
❌ 错误方案：先查后更新（存在竞态条件）
  int count = note.getReplynum();   // 线程A读到 5
  note.setReplynum(count + 1);      // 线程B也读到 5，写 6
  updateById(note);                 // 两个线程都写 6，实际应该是 7

✅ 正确方案：SQL 原子操作
  setSql("replynum = replynum + 1") // MySQL 行锁保证原子性
```

### 5.6 点赞/收藏 —— DB 原子操作 + 演进思路

```java
// 点赞
@PostMapping("/star/{id}")
public R<?> star(@PathVariable Long id) {
    noteService.lambdaUpdate()
            .eq(Note::getId, id)
            .setSql("thumbsupnum = COALESCE(thumbsupnum, 0) + 1")
            .update();
    return R.ok();
}

// 取消收藏（带防负数保护）
@PostMapping("/uncollect/{id}")
public R<?> uncollect(@PathVariable Long id) {
    noteService.lambdaUpdate()
            .eq(Note::getId, id)
            .gt(Note::getFavornum, 0)          // ★ 防负数
            .setSql("favornum = favornum - 1")
            .update();
    return R.ok();
}
```

> **代码注释明确标注了**：“后续迁移到 Redis 异步刷 DB”。这是项目演进思路：先用 DB 快速上线验证业务，再逐步优化到 Redis 异步方案（参考 Strategy 模块的 `incrementCount` + `statisHashMapPersist` 组合）。

### 5.7 路径别名兼容 —— 解决前端路由不一致

`TravelsAliasController` 不设类级别 `@RequestMapping`，直接映射多个不同前缀的路径：

```java
@RestController  // 注意：没有 @RequestMapping 类级别注解
public class TravelsAliasController {

    @GetMapping("/travels/user/query")        // 我的游记
    public R<IPage<Note>> myTravels(NoteQuery qo) { ... }

    @GetMapping("/destinations/regions")      // 写游记-区域列表
    public R<List<Region>> regions(...) { ... }
}
```

**为什么需要这个 Controller？**

因为网关统一前缀 `/note` 将所有 `/note/**` 请求路由到 note 模块，但前端定义的路径种类多样：

| 前端路径 | 实际映射 | 来源 |
|---------|---------|------|
| `/note/notes/query` | NoteController | `@RequestMapping("notes")` |
| `/note/travels/user/query` | TravelsAliasController | 路径别名 |
| `/note/destinations/regions` | TravelsAliasController | 路径别名 |
| `/note/notes/star/{id}` | NoteController | `@RequestMapping("notes")` |

> 如果不用别名 Controller，要么在网关层做复杂的路由规则，要么改前端路径。别名 Controller 是最轻量的方案，一个类解决所有路径兼容问题。

### 5.8 Feign API 包分离设计

本项目采用 "API 包 + 业务实现包" 分离模式：

```
travel-api-note（API 包）          travel-modules-note（业务实现包）
```

> **面试官问：介绍下你做的游记模块？**

**详情聚合上**，用 Feign 跨服务调 member 服务查作者信息，同时做了**降级兜底**：member 服务挂了时，用 Note 表的冗余字段（nickname、headImgUrl）填充，保证详情页不报 500。

**评论系统**的回复数更新用了 `setSql("replynum = replynum + 1")` 的 SQL 原子操作，避免"先查后更新"的并发竞态。

**VO 设计上**，`NoteDetailVO` 继承 `Note`，用 `BeanUtils.copyProperties` 自动拷贝 20+ 基础字段，只补 VO 特有的扩展字段，避免了手动扁平展开的冗余代码。

### 5.10 面试可能追问的问题

**Q1：大字段分离有什么好处？什么场景下应该用？**
A：
- **好处**：① 列表查询不加载大文本，性能提升；② 索引页能容纳更多行，索引效率高；③ 更新主表字段不锁大字段行，并发更好；④ 可以做差异化缓存（主表全量缓存，内容按需加载）。
- **适用场景**：当某列的数据量远大于其他列（如富文本 HTML、JSON 大对象、BLOB 文件），且列表查询通常不需要该列时，就应该分离。
- **本项目**：Note 的 `content` 字段（富文本）和 Strategy 的 `StrategyContent` 都是这个思路。

**Q2：为什么 NoteContent 的 id 不用自增，而是和 Note.id 保持一致？**
A：
- 保证 1:1 关联，`NoteContent.id = Note.id`，查询时直接 `selectById(noteId)`，不需要 JOIN 或额外字段。
- 如果 NoteContent 用自增 id，就需要一个外键字段关联 Note，多一次关联查询。
- 1:1 关系通常用共享主键，这是数据库设计中的常见模式。

**Q3：Feign 调用失败时，你是怎么处理的？**
A：项目中做了两层防护：
1. **代码级 try-catch**：`NoteServiceImpl.detail` 中 try-catch 包裹 Feign 调用，失败时静默降级，用冗余字段兜底。
2. **框架级降级**：`RemoteNoteService` 上声明了 `fallbackFactory = RemoteNoteFallbackFactory.class`，通过 Sentinel 熔断，服务不可用时返回空列表，不会拖垮调用方。

**Q4：评论回复数 +1 为什么用 setSql 而不是先查后更新？**
A：高并发场景下，"先查后更新"存在竞态条件（两个线程同时读到 5，都写 6，实际应该是 7）。`setSql("replynum = replynum + 1")` 利用 MySQL 的行锁机制，`UPDATE ... SET col = col + 1` 是原子操作，保证并发安全。

**Q5：收藏/点赞后续怎么优化？**
A：当前是直接写 DB，高并发下 DB 压力大。后续计划：
1. 学 Strategy 模块的 `incrementCount` 方案，用 **Redis Hash + HINCRBY** 做原子计数。
2. 定时任务 `statisHashMapPersist` 批量刷回 DB。
3. 这样每次点赞只操作 Redis，DB 只做定期持久化，性能提升 10 倍以上。

**Q6：NoteDetailVO 为什么继承 Note，而不是组合一个 Note 字段？**
A：
- **继承**：`BeanUtils.copyProperties(note, vo)` 自动拷贝所有同名字段，一行代码搞定 20+ 字段的赋值，不用手写 `vo.setXxx(note.getXxx())`。
- **组合**：需要 `vo.setNote(note)`，前端访问时要 `vo.note.title` 多一层嵌套，不如 `vo.title` 直观。
- 继承的缺点是 VO 和实体耦合，如果 Note 加了不需要暴露的字段，VO 也会带上。但本项目是内部系统，这个代价可以接受。

**Q7：为什么 Note 里 authorNickname 和 authorHeadImgUrl 标了 `@TableField(exist = false)`？**
A：这两个字段是冗余字段，`ta_note` 表里暂时还没加对应的列。标注 `exist = false` 告诉 MP 这两个字段不对应数据库列，SELECT 时不映射，INSERT/UPDATE 时忽略。后续通过 ALTER TABLE 加列后，去掉这个注解即可。

## 六、Redis 计数 + 异步持久化

> 项目背景：`travel-modules-strategy` 模块中，攻略的阅读量、评论数、点赞数、收藏数、分享数属于**高频写、弱一致性**场景。如果每次点赞都直接 `UPDATE DB`，高并发下数据库会成为瓶颈。本项目采用 **Redis Hash + HINCRBY 原子计数 + 定时任务批量刷回 DB** 的方案，将 DB 写入压力降低 N 倍（N=持久化周期内的请求次数）。

### 6.1 整体架构流程

```
用户点击(阅读/评论/点赞/收藏/分享)
          │
          ▼
StrategyController.viewnumIncr(sid) / replynumIncr(sid)
          │
          ▼
StrategyServiceImpl.incrementCount(sid, "viewnum", 1)  ← 通用增量引擎
          │
          ├─ ① Redis Key 是否存在且完整？
          │       ├─ 否 → loadAndCacheFromDB() 从 DB 预热(SELECT + HSET)
          │       └─ 是 → 跳过
          │
          ├─ ② HINCRBY strategy_status_hash:1001 viewnum 1  ← 原子操作
          │
          └─ ③ HGETALL 返回最新完整 Map
          │
          ▼
【定时任务】statisHashMapPersist()  每 X 分钟执行一次
          │
          ├─ ① KEYS strategy_status_hash:* 匹配所有攻略
          │
          ├─ ② 遍历每个 Key, HGETALL 取出最新数据
          │
          └─ ③ lambdaUpdate() 批量 UPDATE 回 MySQL(5 个字段一次更新)
```

### 6.2 通用增量引擎:incrementCount

这是整个 Redis 计数的核心方法,设计为**通用方法**,支持任意字段、任意增量(+/-),只需一行就能扩展新计数字段。

```java
/**
 * @param sid   攻略ID
 * @param field 统计字段名 "viewnum"/"thumbsupnum"/"replynum"/"sharenum"/"favornum"
 * @param delta 增量(正数加,负数减),如点赞=+1,取消点赞=-1
 */
private Map<String, Object> incrementCount(Long sid, String field, int delta) {
    // 1. 拼 Redis Key
    String key = RedisKeys.STRATEGY_STATIS_HASH.join(sid.toString());

    // 2. 缓存不存在或不完整 → 从 DB 预热
    Map<String, Object> map = redisService.getCacheMap(key);
    if (!isMapComplete(map)) {
        map = loadAndCacheFromDB(sid, key);
    }

    // 3. HINCRBY 原子增加(并发安全)
    redisService.incrementCacheMapValue(key, field, delta);

    // 4. 返回最新完整数据
    return redisService.getCacheMap(key);
}
```

**上层调用**:

```java
// 阅读量+1
public Map<String, Object> viewnumIncr(Long sid) {
    return incrementCount(sid, "viewnum", 1);
}

// 评论数+1
public Map<String, Object> replynumIncr(Long sid) {
    return incrementCount(sid, "replynum", 1);
}

// ✅ 扩展点赞只需一行
public Map<String, Object> thumbsupnumIncr(Long sid) {
    return incrementCount(sid, "thumbsupnum", 1);
}
// ✅ 扩展取消收藏只需一行
public Map<String, Object> favornumDecr(Long sid) {
    return incrementCount(sid, "favornum", -1);
}
```

> **面试点**:开闭原则的体现 —— 新增计数字段无需修改 `incrementCount` 核心逻辑,只需在上层加一行调用。参数化替代硬编码,避免代码重复 5 倍。

### 6.3 缓存预热:loadAndCacheFromDB

当 Redis 中不存在该攻略的 Hash 时,从 DB 加载完整数据一次性写入:

```java
private Map<String, Object> loadAndCacheFromDB(Long sid, String key) {
    Strategy strategy = baseMapper.selectById(sid);
    Map<String, Object> map = new HashMap<>();
    map.put("id",          strategy.getId());
    map.put("viewnum",     strategy.getViewnum().intValue());
    map.put("thumbsupnum", strategy.getThumbsupnum().intValue());
    map.put("replynum",    strategy.getReplynum().intValue());
    map.put("sharenum",    strategy.getSharenum().intValue());
    map.put("favornum",    strategy.getFavornum().intValue());
    // ★ 一次性写入所有 6 个字段,而不是只写当前用到的 viewnum
    redisService.setCacheMap(key, map);
    return map;
}
```

**为什么一次性写所有字段,而不是只写当前用到的?**

`isMapComplete` 校验的是全部 6 个字段,如果只写 `viewnum`,下次有人点赞时会发现缓存不完整,又触发一次 DB 查询。一次性预热全部字段,后续所有操作都直接走 Redis,避免多次重复加载。

### 6.4 定时持久化:statisHashMapPersist

把 Redis 中的计数批量刷回 DB,保证数据最终落盘:

```java
public void statisHashMapPersist() {
    // 1. 匹配所有攻略的 Key
    String key = RedisKeys.STRATEGY_STATIS_HASH.join("*");
    Collection<String> keys = redisService.keys(key);

    for (String k : keys) {
        Map<String, Object> cacheMap = redisService.getCacheMap(k);
        Long id          = (Long) cacheMap.get("id");
        Integer viewnum  = (Integer) cacheMap.get("viewnum");
        Integer thumbsupnum = (Integer) cacheMap.get("thumbsupnum");
        Integer replynum    = (Integer) cacheMap.get("replynum");
        Integer sharenum    = (Integer) cacheMap.get("sharenum");
        Integer favornum    = (Integer) cacheMap.get("favornum");

        // ★ 5 个字段一次 UPDATE,而不是每个字段一条 SQL
        lambdaUpdate()
                .eq(Strategy::getId, id)
                .set(Strategy::getViewnum, viewnum)
                .set(Strategy::getThumbsupnum, thumbsupnum)
                .set(Strategy::getReplynum, replynum)
                .set(Strategy::getSharenum, sharenum)
                .set(Strategy::getFavornum, favornum)
                .update();
    }
}
```

> **设计要点**:5 个字段合成一条 UPDATE SQL,而不是每个字段一条。假设 1000 条攻略,1 次持久化只执行 1000 条 SQL,而不是 5000 条。

### 6.5 Redis 存储结构

```
Key:     strategy_status_hash:1001        ← 前缀 + 冒号 + 攻略ID
Type:    Hash
TTL:     -1（永不过期,由定时任务管理）

Fields:
  id          → 1001                       攻略ID
  viewnum     → 1523                       阅读量
  thumbsupnum → 89                         点赞数
  replynum    → 45                         评论数
  sharenum    → 12                         分享数
  favornum    → 67                         收藏数
```

**底层 Redis 命令映射**:

| 业务操作 | Redis 命令 | Java 代码 |
|---------|-----------|----------|
| 缓存预热 | `HSET key id 1001 viewnum 0 ...` | `redisTemplate.opsForHash().putAll(key, map)` |
| 阅读量+1 | `HINCRBY key viewnum 1` | `redisTemplate.opsForHash().increment(key, "viewnum", 1)` |
| 获取全部 | `HGETALL key` | `redisTemplate.opsForHash().entries(key)` |
| 批量查找 | `KEYS strategy_status_hash:*` | `redisService.keys(pattern)` |

### 6.6 为什么选 Hash 而不是 String(JSON)?

| 对比维度 | String(JSON)方案 | Hash 方案(本项目) |
|---------|-----------------|------------------|
| 单字段修改 | GET → 反序列化 → 改字段 → 序列化 → SET(多步,非原子) | 直接 `HINCRBY`(一步,原子) |
| 并发安全 | ❌ 竞态风险(两个请求同时读到相同值) | ✅ Redis 单线程,`HINCRBY` 天然原子 |
| 网络开销 | 每次传整个 JSON(5 个字段都传) | 只传改变的字段(1 个 field + delta) |
| 内存占用 | 每个攻略一个独立 String,无法共享编码 | Hash 内部 ziplist/listpack 紧凑编码,内存更省 |
| 单字段读取 | 反序列化整个 JSON 才能拿到 viewnum | `HGET key viewnum` 一步到位 |
| 扩展性 | 加字段要改 JSON 结构,可能兼容问题 | 加字段直接 `HSET key newfield value`,零侵入 |

### 6.7 面试答题模板(结合项目)

> **面试官问:点赞/收藏这种高频计数你是怎么实现的?**

**答:** 我项目里攻略模块的 5 种计数(阅读量、点赞、评论、分享、收藏)用的是 **Redis Hash + HINCRBY 原子操作 + 定时任务批量刷回 DB** 的方案。

**写路径上**,用户每次点赞时,先查 Redis 中是否存在该攻略的 Hash 缓存,如果不存在就从 DB 加载完整数据做一次**缓存预热**(一次性写入 5 个字段,避免后续操作重复触发 DB)。然后用 `HINCRBY` 命令对对应字段做原子加一,这一步是 Redis 单线程保证并发安全的,不会有竞态问题。

**通用方法设计上**,我把计数逻辑抽成了一个 `incrementCount(sid, field, delta)` 方法,field 可以是 5 个字段中的任意一个,delta 支持正负(点赞+1,取消收藏-1)。这样新增一个计数字段只需在上层调用一行,不用写重复代码,符合开闭原则。

**持久化上**,我用了定时任务 `statisHashMapPersist`,每 X 分钟把 Redis 里所有攻略的计数**批量 UPDATE**回 MySQL。注意是 5 个字段合成一条 SQL,而不是每个字段一条。这样做把 N 次 DB 写入合并成了 1 次,DB 压力降低 N 倍。

**一致性上**,我选择的是**最终一致性**而非强一致性。对于点赞和阅读量,丢失几秒的数据可以接受,这个 trade-off 换来了极高的写入性能。如果业务需要强一致性(比如钱包余额),就不能用这个方案,得走实时双写加分布式事务。

### 6.8 面试可能追问的问题

**Q1:为什么用 HINCRBY 而不是 GET → +1 → SET?**
A:
- `HINCRBY` 是 Redis 内置的**原子操作**,Redis 单线程模型保证不会有并发问题。
- `GET → +1 → SET` 是三步操作,非原子:两个请求同时读到 100,都设置为 101,就会丢失一次计数。
- 类比 Note 模块的 `setSql("replynum = replynum + 1")`,原理完全一样,MySQL 靠行锁保证原子性,Redis 靠单线程。

**Q2:缓存预热时为什么一次性写所有 5 个字段,而不是只写当前用到的?**
A:
- 因为 `isMapComplete` 校验的是全部字段是否都存在。如果只写 `viewnum`,下次有人点赞时会发现缓存不完整,又触发一次 DB 查询。
- 一次性预热所有字段,后续所有操作都直接走 Redis,避免多次重复加载。
- 这也是**写放大换读效率**的思想:第一次多写几个字段,后面所有读都省了。

**Q3:Redis 和 DB 数据不一致怎么办?**
A:
- 本项目采用**最终一致性**方案:Redis 是实时数据,DB 是定时持久化的历史数据。两者允许短暂不一致。
- **读操作优先走 Redis**,Redis 挂了才回源 DB(代码里 `loadAndCacheFromDB` 就是回源逻辑)。
- **宕机恢复**:如果 Redis 重启清空了数据,下一次请求会自动从 DB 预热回来,只是那一次会走 DB。
- **Trade-off**:牺牲了强一致性,换来了高并发下的写入性能。对于点赞/阅读量,丢失几秒的数据可以接受。

**Q4:KEYS 命令在生产环境有性能风险,怎么优化?**
A:
- `KEYS *` 会阻塞 Redis(单线程),如果有 100 万条 key,可能卡顿几百毫秒,期间 Redis 无法响应其他请求。
- **生产环境应改用 `SCAN` 命令**:游标遍历,分批次读取,不会阻塞 Redis。
- `SCAN 0 MATCH strategy_status_hash:* COUNT 1000`,循环直到游标返回 0。
- 当前项目数据量小,`KEYS` 可以接受,但面试时要主动提这个优化方向,体现生产意识。

**Q5:为什么不用实时双写(Redis 和 DB 同时写)?**
A:
- **性能**:实时双写每次请求要写两个存储,不仅慢(磁盘 I/O + 网络),还会引入分布式事务问题(一个成功一个失败怎么办?)。
- **定时持久化的好处**:把 N 次 DB 写合并成 1 次批量更新,DB 压力降低 N 倍。
- **什么时候用实时双写**:如果业务要求强一致性(如订单状态、钱包余额),不能丢数据,那就得实时双写+分布式事务。对于点赞/阅读量,用最终一致性更合适。

**Q6:如果 Redis 挂了,计数功能会怎么样?**
A:
- 本项目的 `loadAndCacheFromDB` 里有 DB 回源机制:如果 Redis 里取不到,就从 DB 加载。
- 但是**写操作目前还是只写 Redis**,如果 Redis 挂了,`incrementCacheMapValue` 会抛异常,计数功能就不可用了。
- **优化方案**(面试可以主动提):
  1. 加熔断降级:Redis 不可用时,降级成直接 `UPDATE DB SET x = x + 1` 的 SQL 原子操作。
  2. Redis 恢复后,再把这段时间 DB 的计数同步回 Redis(或直接以 DB 为准,下次请求时自动预热)。
- 这就是 Note 模块当前用的方案,作为兜底完全可行。

**Q7:这个方案和 Note 模块的直接 DB UPDATE 有什么关系?为什么两个模块方案不一样?**
A:
- **Strategy 模块**:业务上计数频率高(攻略详情页每次打开都加 viewnum),且攻略数量相对少,适合 Redis Hash 方案。
- **Note 模块**:当前是 MVP 快速上线阶段,直接用 `setSql("replynum = replynum + 1")` 原子 UPDATE,代码简单,快速验证业务。
- Note 模块的点赞/收藏代码里**明确标注了 "后续迁移到 Redis 异步刷 DB"**,这就是演进路线。
- **核心思想**:业务不同阶段选不同方案。早期简单快速上线,后期用户量上来再迁移到 Redis 方案。不要过早优化,也不能不考虑优化空间。

**Q8:如果要记录"哪个用户给哪篇攻略点过赞"(防止重复点赞),怎么扩展?**
A:
- 当前方案只记录"每篇攻略被点赞多少次",不管是谁点的,所以用户可以无限点赞。
- 要做防重复点赞,需要存**用户-攻略的关联关系**,常见方案:
  1. **Redis Set**:Key = `strategy_thumbsup:1001`,Value = Set of userId。点赞时 `SADD`,判断 `SISMEMBER` 是否已存在。缺点:内存占用大,数据无法持久化。
  2. **Redis Bitmap**:Key = `strategy_thumbsup_bitmap:1001`,offset = userId。`SETBIT` 设置,`GETBIT` 判断。优点:极度节省内存(1 亿用户只要 12.5MB)。缺点:userId 必须是连续整数,稀疏 ID 浪费空间。
  3. **DB 持久化表**:新建 `ta_strategy_thumbsup(strategy_id, user_id, create_time)` 表,联合唯一索引防重复。
- 通常是**Redis + DB 组合**:Redis 做实时防重判断(Set/Bitmap),异步写 DB 做持久化,DB 冷数据定时删除。

## 七、游记模块 Redis 计数升级（Note → Redis）

### 7.1 升级背景

游记模块（travel-modules-note）原先的观看/点赞/评论/收藏功能**全部直接走数据库 SQL +1**：

```java
// 旧代码：直接 DB +1，每次操作都打数据库
noteService.lambdaUpdate()
    .eq(Note::getId, id)
    .setSql("thumbsupnum = COALESCE(thumbsupnum, 0) + 1")
    .update();
```

**问题**：高并发场景下（如热门游记被频繁浏览/点赞），每次操作都打 DB，数据库压力大；且没有收藏关系记录，无法判断用户是否已收藏；点赞无限制，可无限刷。

**解决方案**：参照同项目 strategy 模块的成熟模式，引入 **Redis Hash + HINCRBY 原子计数 + 定时任务异步刷库**。

### 7.2 Redis 数据结构设计

| Redis Key 枚举 | 前缀 | 过期时间 | 数据结构 | 用途 |
|---|---|---|---|---|
| `NOTE_STATIS_HASH` | `note_statis_hash` | -1（永不过期） | Hash | 每篇游记的统计计数（viewnum/thumbsupnum/replynum/sharenum/favornum） |
| `NOTE_FAVOR_SET` | `note_favor_set` | -1（永不过期） | Set | 记录每个用户收藏了哪些游记（userId → Set of noteId） |
| `USER_NOTE_THUMBSUP` | `user_note_thumbsup` | 86400（24小时） | String | 每个用户对每篇游记的每日点赞次数（nid:uid → count） |

**Key 拼接示例**：
```
note_statis_hash:101              → {id:101, viewnum:500, thumbsupnum:30, replynum:15, sharenum:5, favornum:20}
note_favor_set:1001               → {101, 105, 200}  （用户1001收藏了游记101、105、200）
user_note_thumbsup:101:1001       → 3  （用户1001今天对游记101点赞了3次）
```

### 7.3 核心流程

#### 流程一：浏览/评论计数 +1（通用 incrementCount 方法）

```
前端请求 → Controller → Service.incrementCount(nid, field, delta)
    │
    ├─ 1. 从 Redis Hash 获取当前游记的统计 Map
    │
    ├─ 2. 检查 Map 是否完整（包含 id + 5 个计数字段）
    │   ├─ 完整 → 直接 HINCRBY 原子 +1
    │   └─ 不完整/不存在 → 从 DB 加载完整数据写入缓存，再 HINCRBY
    │
    └─ 3. 返回更新后的完整统计 Map
```

**核心代码**（NoteServiceImpl）：

```java
private Map<String, Object> incrementCount(Long nid, String field, int delta) {
    String key = RedisKeys.NOTE_STATIS_HASH.join(nid.toString());

    // 1. 检查缓存是否完整，不完整则从 DB 加载（懒加载模式）
    Map<String, Object> map = redisService.getCacheMap(key);
    if (!isMapComplete(map)) {
        map = loadAndCacheFromDB(nid, key);
    }

    // 2. 原子增加（底层 HINCRBY，线程安全）
    redisService.incrementCacheMapValue(key, field, delta);

    // 3. 返回最新数据
    return redisService.getCacheMap(key);
}
```

#### 流程二：收藏/取消收藏（切换状态）

```
前端 POST /notes/collect/{id} → Service.favor(nid)
    │
    ├─ 1. 从 Redis Set 检查用户是否已收藏（SISMEMBER）
    │   ├─ 已收藏 → HINCRBY favornum -1 + SREM 移除收藏关系
    │   └─ 未收藏 → HINCRBY favornum +1 + SADD 记录收藏关系
    │
    └─ 2. 返回 {result: true/false, ...统计Map}
```

**优化点**：旧代码需要两个接口（collect + uncollect），新代码合并为一个 toggle 接口，前端只需调一个接口。

#### 流程三：点赞（每日限 5 次）

```
前端 POST /notes/star/{id} → Service.thumbsup(nid)
    │
    ├─ 1. 拼接限流 key：user_note_thumbsup:{nid}:{uid}
    │
    ├─ 2. key 不存在 → 设置初始值 0，过期时间为今天剩余时间
    │
    ├─ 3. INCR 原子 +1，判断返回值
    │   ├─ > 5 → 点赞失败（今日已达上限）
    │   └─ ≤ 5 → HINCRBY thumbsupnum +1
    │
    └─ 4. 返回 {result: true/false, ...统计Map}
```

#### 流程四：定时持久化（Redis → DB）

```
Quartz 定时任务 → NoteTask.statisHashMapPersist()
    │
    ├─ Feign 调用 → NoteController /feign/statisHashMapPersist
    │
    ├─ 1. KEYS note_statis_hash:* 获取所有游记的统计 key
    │
    ├─ 2. 遍历每个 key，HGETALL 获取完整统计 Map
    │
    └─ 3. 批量 UPDATE ta_note SET viewnum=?, thumbsupnum=?, ...
```

#### 流程五：应用启动预热

```
ApplicationReadyEvent → NoteStatisHashInitListener
    │
    ├─ 1. 查询 DB 中所有游记
    │
    ├─ 2. 遍历每篇游记，拼接 key
    │
    ├─ 3. 判断 key 是否已存在（避免覆盖已有缓存）
    │
    └─ 4. 不存在 → 将统计数据写入 Redis Hash
```

### 7.6 面试问答模板

**Q: 游记模块的浏览/点赞/评论/收藏是怎么实现的？**

A: 我们采用了 **Redis Hash + HINCRBY 原子计数 + 定时任务异步刷库** 的方案。每篇游记在 Redis 中对应一个 Hash key（`note_statis_hash:{id}`），包含 viewnum、thumbsupnum、replynum、sharenum、favornum 五个字段。用户操作时通过 HINCRBY 原子增减，不直接打数据库。定时任务（Quartz + Feign）每隔一段时间扫描所有 key，批量 UPDATE 回数据库。

**Q: 为什么要用 Redis 而不是直接操作数据库？**

A: 三个原因：
1. **性能**：浏览/点赞是高频操作，直接打 DB 会造成行锁竞争和 IO 瓶颈。Redis 全内存操作，HINCRBY 是 O(1) 的原子命令。
2. **原子性**：HINCRBY 本身是原子的，不需要额外加锁，并发安全。
3. **削峰**：高并发时 Redis 做缓冲，定时任务批量刷库，DB 压力从 N 次写降为 1 次写。

**Q: 缓存数据怎么初始化的？如果 Redis 挂了怎么办？**

A: 两层保障：
1. **启动预热**：应用启动时（ApplicationReadyEvent），NoteStatisHashInitListener 把 DB 中所有游记的统计数据预加载到 Redis，避免冷启动。
2. **懒加载兜底**：incrementCount 方法中检查 Map 是否完整，如果不完整（Redis 重启后丢失），自动从 DB 加载并写入缓存。即使 Redis 挂了恢复后，下次访问也能自动重建缓存。

**Q: 点赞怎么防刷？**

A: 用 Redis 的 String 类型做每日限流。Key = `user_note_thumbsup:{游记id}:{用户id}`，过期时间设为今天剩余时间（到 23:59:59）。每次点赞 INCR +1，超过 5 次就拒绝。第二天 key 自动过期，重新计数。

**Q: 收藏功能怎么实现的？**

A: 用 Redis Set 记录用户的收藏关系。Key = `note_favor_set:{用户id}`，Value = Set of 游记id。收藏时 SADD + HINCRBY favornum +1，取消收藏时 SREM + HINCRBY favornum -1。查详情时用 SISMEMBER 判断是否已收藏，设置 favorFlag 返回前端。

**Q: 定时任务怎么配置的？**

A: 在 job 模块（travel-modules-job）中创建 NoteTask 类，通过 Feign 调用 note 服务的 `/feign/statisHashMapPersist` 接口。然后在管理后台的 sys_job 表中配置 Quartz 定时任务，invokeTarget 设为 `noteTask.statisHashMapPersist`，设置 cron 表达式（如每 10 分钟执行一次）。
