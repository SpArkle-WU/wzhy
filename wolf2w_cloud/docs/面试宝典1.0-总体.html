一、Spring Cloud Alibaba 微服务架构 高频

1.1 你们项目为什么要拆微服务？拆分依据是什么？

为什么要拆微服务？

单体架构在业务增长后面临：代码耦合严重、部署效率低、扩容只能整体扩容、技术栈受限等问题。拆分微服务后，各服务独立部署、独立扩容、团队分工明确。

拆分依据：按业务领域拆分。趣谷集项目拆为用户中心、资讯服务、社区服务、搜索中心、AI问答、秒杀等 10+ 模块。例如资讯和社区是不同的业务领域，写多读少 vs 读多写少，扩容策略不同，适合拆开。

1.2 Nacos 作为注册中心，服务注册与发现原理？

Nacos 注册中心原理？

服务注册：服务启动时向 Nacos Server 发送注册请求，包含 IP、端口、服务名等信息。Nacos 维护一个服务实例列表（内存 Map）。

服务发现：消费方从 Nacos 拉取服务实例列表并缓存到本地，通过 Ribbon/LoadBalancer 做客户端负载均衡选择实例。

健康检查：临时实例（默认）使用客户端心跳模式，5秒一次心跳，15秒未收到标记不健康，30秒剔除。永久实例使用服务端主动探测。

1.3 Nacos 既是注册中心又是配置中心，配置动态刷新怎么实现的？

Nacos 配置动态刷新原理？

Nacos 客户端通过长轮询（Long Polling）监听配置变更。客户端发起 HTTP 请求到 Nacos Server，默认 30 秒超时。如果期间配置没有变化，Server 持有请求 29.5 秒后返回空；如果配置发生变化，Server 立即返回变更的 dataId，客户端再发起请求获取最新配置内容。

配合 @RefreshScope 注解，Bean 会在配置变更时自动重建，实现热更新。

二、Gateway 网关治理 高频

2.1 Gateway 四层过滤器链分别做什么？

图 2.1 Gateway 四层过滤器链执行流程
四层过滤器链的职责？

第一层：统一鉴权 — AuthFilter 解析 JWT Token，校验合法性，将用户 ID、用户名写入请求头透传给下游服务。/admin/ 路径强制校验 Token，非 admin 路径无 Token 也放行。

第二层：验证码校验 — 登录接口请求需携带验证码，Filter 拦截后从 Redis 取出验证码与请求参数比对。

第三层：XSS 防护 — 对请求参数做 HTML 转义，防止跨站脚本攻击，过滤 <script> 等危险标签。

第四层：黑名单拦截 — 从 Redis 读取被封禁的 IP 列表，命中则直接返回 403。

2.2 Gateway 为什么选择 WebFlux 而不是 Spring MVC？

Gateway 为什么用 WebFlux？

Gateway 基于 WebFlux + Netty，是非阻塞异步的。网关作为所有请求的入口，并发量极高，传统 Servlet 容器（Tomcat）一个请求占一个线程，高并发下线程耗尽。WebFlux 基于 Reactor 响应式编程，少量线程即可处理大量连接，I/O 利用率更高。

2.3 Gateway 的路由是怎么配置的？

路由配置方式？

在 Nacos 配置中心的 travel-gateway-dev.yml 中配置：

spring:
  cloud:
    gateway:
      routes:
        - id: travel-note
          uri: lb://travel-note
          predicates:
            - Path=/notes/**
        - id: travel-strategy
          uri: lb://travel-strategy
          predicates:
            - Path=/strategies/**

lb:// 表示负载均衡，Gateway 从 Nacos 拉取服务实例列表，通过 Ribbon 做负载均衡选择一个实例转发请求。

面试话术：「Gateway 四层过滤器链按顺序执行——鉴权→验证码→XSS→黑名单，任何一层拦截就直接返回不进下一层。选 WebFlux 而非 Spring MVC 是因为网关是所有请求入口，并发量极高，WebFlux 基于 Reactor 异步非阻塞，少量线程处理大量连接。路由配置在 Nacos 的 yml 中管理，lb:// 前缀表示负载均衡，Gateway 从 Nacos 拉取实例列表自动做负载均衡转发。」

三、JWT + Redis 认证体系 高频

3.1 JWT + Redis 双存储方案怎么设计的？

图 3.1 JWT + Redis 双存储认证全流程
JWT + Redis 双存储方案？

JWT 负载：存储用户基本信息（userId、username），签名后生成 Token，无状态，不需要查库就能解析用户身份。

Redis 辅助：JWT 本身无法主动失效（签发后到过期前一直有效），所以把 Token 也存一份到 Redis，Key 为 login_tokens:uuid。每次鉴权时除了校验 JWT 签名，还要检查 Redis 中是否存在该 Token。

强制下线：直接删除 Redis 中的 Token 记录，用户下次请求时鉴权失败。

滑动续期：用户活跃时（距离过期不到 20 分钟），自动刷新 Redis 中 Token 的过期时间，实现无感续期。

3.2 JWT 的结构是什么？

JWT 三段结构？

JWT 由三部分组成，用 . 分隔：Header.Payload.Signature

Header：Token 类型和签名算法，如 {"typ":"JWT","alg":"HS512"}

Payload：携带的声明数据，如 userId、username、过期时间。注意不要放敏感信息，因为 Payload 只做 Base64 编码，不加密。

Signature：将 Header + Payload 用密钥做 HS512 签名，防篡改。

3.3 为什么不纯用 JWT，要加 Redis？

纯 JWT 的问题？

纯 JWT 有两个致命问题：①无法主动失效——用户退出登录、修改密码、管理员封号后，JWT 在过期前仍然有效；②无法多端互踢——同一用户在多设备登录，无法踢掉旧设备的 Token。

引入 Redis 后，Token 生命周期由 Redis 控制，可以随时删除实现主动失效。代价是多了一次 Redis 查询，但 Redis 是内存操作，性能可接受。

面试话术：「我设计的 JWT + Redis 双存储方案核心是——JWT 负责无状态解析用户身份（不用查库），Redis 负责控制 Token 生命周期（主动失效、多端互踢、滑动续期）。纯 JWT 最大问题是签发后到过期前一直有效，用户退出登录、管理员封号都无法让 Token 失效。引入 Redis 后每次鉴权多查一次 Redis，但 Redis 是内存操作性能可接受。滑动续期是检查 TTL 剩余不到 20 分钟就自动续期到 30 分钟，用户活跃期间不掉线。」

四、OpenFeign + Sentinel 服务间调用 高频

4.1 OpenFeign 跨服务调用怎么做的？

Feign 调用流程？

1. 定义 Feign 接口，用 @FeignClient 注解指定服务名和降级工厂：

@FeignClient(name = "travel-note", fallbackFactory = RemoteNoteFallbackFactory.class)
public interface RemoteNoteService {
    @GetMapping("/notes/feign/{id}")
    R getOne(@PathVariable Long id, @RequestHeader String source);
}

2. 调用时就像调本地方法一样，Feign 底层通过 Ribbon 从 Nacos 拉取实例列表做负载均衡，发起 HTTP 请求。

3. 内部调用通过 @InnerAuth + from-source=inner 请求头标识，确保接口仅允许微服务内部调用。

4.2 Feign 调用失败时降级怎么处理的？

降级兜底策略？

通过 FallbackFactory 实现降级。例如游记详情页需要调 member 服务查作者信息，如果 member 服务挂了：

① FallbackFactory 捕获异常，返回 R.fail()；

② 游记表中冗余了 author_id，即使查不到用户详细信息，游记主体内容仍可正常展示；

③ 评论表冗余了 note_title，查评论时不需要再连表查游记标题。

设计思路：核心链路（游记列表、详情主体）不依赖跨服务调用，关联数据（用户头像、目的地详情）做降级容错。

4.3 Sentinel 的限流和熔断降级有什么区别？

限流 vs 熔断？

限流：控制请求速率，超过阈值的请求直接拒绝。秒杀场景用令牌桶限流，防止瞬时流量压垮服务。Sentinel 基于滑动时间窗口统计 QPS。

熔断：当下游服务异常率（异常比例/慢调用比例）超过阈值时，熔断器打开，直接走降级逻辑，不再调用下游。过一段恢复时间后进入半开状态，放一个请求试探，成功则关闭熔断器。

降级：熔断后执行 fallback 逻辑，返回兜底数据，保证用户体验。

4.4 Sentinel 的滑动时间窗口算法怎么理解？

滑动时间窗口原理？

Sentinel 把 1 秒划分为 2 个 500ms 的时间窗口。统计时取当前窗口 + 前一个窗口的数据，形成滑动效果。比如设置 QPS 阈值 100，如果当前 500ms 内已有 60 个请求，前 500ms 有 50 个请求，合计 110 > 100，直接拒绝后续请求。

相比固定窗口算法，滑动窗口避免了窗口边界处的突发流量问题。

面试话术：「跨服务调用我用 OpenFeign 声明式接口，像调本地方法一样调远程服务。降级用 FallbackFactory——比如游记详情页要调 member 服务查作者信息，如果 member 挂了，FallbackFactory 捕获异常返回 null，但游记表冗余了 author_id 和 author_name，主体内容仍可展示。设计思路是核心链路不依赖跨服务调用，关联数据做降级容错。Sentinel 的限流用滑动时间窗口算法，1 秒分 2 个 500ms 窗口，取当前+前一个窗口合计判断，避免窗口边界突发流量问题。」

5.2 Redis 持久化 RDB 和 AOF 的区别？

RDB vs AOF？
对比项RDBAOF
原理定时全量快照，fork 子进程生成 .rdb 文件追加写命令到 .aof 文件

5.3 Redis 过期删除策略和内存淘汰策略？

过期删除 + 内存淘汰？

过期删除策略（Key 到期后怎么删）：

①惰性删除：访问 Key 时才检查是否过期，过期则删除。优点 CPU 友好，缺点大量过期 Key 不访问会占内存。

②定期删除：每隔一段时间随机抽取一批 Key 检查过期，删除已过期的。Redis 默认每秒 10 次，每次检查 20 个 Key。

Redis 采用惰性 + 定期组合策略。

内存淘汰策略（内存满了怎么办）：

① noeviction：不淘汰，写入直接报错（默认）

② allkeys-lru：所有 Key 中淘汰最近最少使用的（推荐）

③ volatile-lru：只在设了过期时间的 Key 中淘汰 LRU

④ allkeys-lfu：所有 Key 中淘汰最不经常使用的（Redis 4.0+）

5.4 缓存穿透、击穿、雪崩怎么解决？

缓存三大问题？

5.5 Redis Hash + HINCRBY 原子计数怎么用的？

计数方案？

游记的浏览数、点赞数、收藏数、评论数用 Redis Hash 存储：

# Key: note:stats:{noteId}
# Field: viewnum / thumbsupnum / favornum / replynum

HINCRBY note:stats:1001 viewnum 1      # 浏览 +1
HINCRBY note:stats:1001 thumbsupnum 1   # 点赞 +1
HGETALL note:stats:1001                  # 获取所有计数

为什么用 HINCRBY：Redis 单线程执行，HINCRBY 是原子操作，不会出现并发计数错误。比 GET → +1 → SET 三步操作安全。

刷库策略：定时任务每隔 5 分钟扫描 Redis 中的计数，批量 UPDATE 到 MySQL，避免每次点赞都写库。

面试话术：「Redis 在我项目中有六大应用场景——Token 存储用 String、验证码用 String、秒杀库存用 String 做 Lua 原子扣减、浏览量点赞计数用 Hash + HINCRBY 原子递增、黑名单 IP 用 Set、热点数据缓存用 String。Key 前缀用枚举类统一管理，避免命名冲突和过期时间散落难维护。缓存三大问题也做了防护——穿透用缓存空值、击穿用 SETNX 互斥锁、雪崩用 TTL 加随机值。秒杀场景 Redis 宕机了直接返回'系统繁忙'，宁可不卖不能超卖。」

六、RabbitMQ 消息队列 高频

6.1 项目中 RabbitMQ 用在哪些场景？

RabbitMQ 应用场景？

①秒杀异步下单：用户秒杀成功后，Producer 发消息到队列，直接返回"排队中"。Consumer 端按能力消费，批量写入数据库，削峰填谷。

②超时订单取消：下单后发一条 TTL 消息到延迟队列，30 分钟未支付则消息过期进入死信队列，Consumer 消费死信队列执行取消逻辑。

③社区通知：点赞、评论后异步发消息通知作者，解耦核心业务与通知逻辑。

6.2 RabbitMQ 怎么保证消息不丢失？

消息可靠性保证？

三个环节保证：

① 生产者确认（Producer → Broker）：开启 publisher-confirms，Broker 收到消息后回 ACK 给生产者。如果没收到 ACK，生产者重发。

② 消息持久化（Broker 存储）：交换机、队列、消息都设置 durable=true，消息写入磁盘，Broker 重启不丢。

③ 消费者手动 ACK（Broker → Consumer）：消费者处理完业务逻辑后手动 basicAck。如果处理异常，basicNack 拒绝消息，消息回到队列重试。

6.3 死信队列怎么实现超时订单取消？

死信队列实现延迟取消？

死信（DLX）触发条件：①消息被 basicNack 且 requeue=false；②消息 TTL 过期；③队列达到最大长度。

实现方案：

@Bean
public Queue deadLetterQueue() {
    return QueueBuilder.durable("order.dlq")
        .withArgument("x-dead-letter-exchange", "order.exchange")
        .build();
}

// 2. 声明延迟队列，绑定死信交换机，设置 TTL=30min
@Bean
public Queue delayQueue() {

        .withArgument("x-dead-letter-exchange", "order.dlx")
        .withArgument("x-message-ttl", 1800000)  // 30分钟
        .build();
}

// 3. 下单时发消息到延迟队列

@RabbitListener(queues = "order.dlq")

    // 检查订单状态，未支付则取消
}

6.4 消息重复消费怎么处理？

消息幂等性？

网络问题导致 ACK 丢失，Broker 会重投消息。解决方案：

方案一：业务唯一键去重——消费前查 Redis 是否已处理过该消息 ID，处理过则直接 ACK 跳过。

方案二：数据库唯一索引——订单号设唯一索引，重复插入会报错，捕获异常后 ACK。

方案三：状态机校验——订单状态为"待支付"才执行取消，已经是"已取消"则跳过。

面试话术：「RabbitMQ 在项目中三个场景——秒杀异步下单、超时订单取消、社区通知。消息可靠性三重保证：生产者 confirm 确认、消息和队列持久化、消费者手动 ACK。超时取消用死信队列——下单时发一条 TTL=30 分钟的消息到延迟队列，过期后进入死信队列被消费执行取消逻辑。消息重复消费用业务唯一键去重——消费前查 Redis 是否已处理过该消息 ID，处理过直接 ACK 跳过。」

3. 用户点击秒杀 → Lua 脚本原子扣减 Redis 库存（检查库存 > 0 + 扣减 + 记录用户已购买，防重复购买）

4. 库存扣减成功 → 发消息到 RabbitMQ → 返回"排队中"

5. Consumer 消费消息 → 创建订单写入 DB → 扣减 DB 库存

第三阶段：秒杀后

7.2 Lua 脚本防超卖的原理？

Lua 脚本防超卖？
-- KEYS[1] = seckill:stock:{skuId}
-- KEYS[2] = seckill:users:{skuId} (已购买用户集合)
-- ARGV[1] = userId

-- 1. 检查库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then return -1 end  -- 库存不足

-- 2. 检查是否已购买（防重复）
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2  -- 重复购买
end

-- 3. 扣减库存 + 记录用户
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1  -- 成功

为什么用 Lua：Redis 执行 Lua 脚本是原子的（单线程），中间不会被其他命令插入。如果用 GET → 判断 → DECR 三条命令，高并发下可能出现两个请求同时 GET 到库存=1，都判断为 > 0，都 DECR 导致超卖。

7.3 三级缓存怎么设计的？

Caffeine → Redis → DB 三级缓存？

第一级：Caffeine 本地缓存（JVM 内存）—— 存储热点商品信息，TTL 10秒。读取最快（纳秒级），但容量有限、多节点不一致。

第二级：Redis 分布式缓存—— TTL 5分钟。所有节点共享，一致性较好。Caffeine miss 后查 Redis。

第三级：MySQL 数据库—— Redis miss 后查 DB，查到后回写 Redis 和 Caffeine。

缓存更新策略：商品信息变更时，先更新 DB，再删除 Redis 缓存（Cache Aside 模式），Caffeine 靠短 TTL 自然过期。

面试话术：「秒杀设计核心三阶段——预热阶段把库存写入 Redis + Caffeine 三级缓存；秒杀阶段用 Redis Lua 脚本原子操作检查库存+检查重复购买+扣减库存三步，避免超卖；异步阶段用 RabbitMQ 削峰，Consumer 按能力消费写库。Lua 脚本防超卖的原理是 Redis 单线程执行 Lua 不会被其他命令插入，如果用 GET→判断→DECR 三条命令中间有并发间隙会导致超卖。超时未支付用死信队列自动取消并回补库存。」

9.1 RAG 的完整流程是什么？

RAG 流程？

离线建库阶段：

1. 收集周边资讯语料（文章、商品描述等）

2. 用 bge-zh 模型将文本转为向量（Embedding），每段文本对应一个高维向量

9.2 为什么要双路召回？只用向量不行吗？

双路召回的必要性？

向量召回擅长语义匹配（"手办" ≈ "模型玩具"），但对专有名词（IP名、人名）容易召回不相关内容。关键词召回精确但无法理解同义词。

双路召回互补：关键词召回保证精确性，向量召回补充语义相关性，RRF 融合取两者优点。

9.3 RRF 融合排序是什么？

RRF 算法？

Reciprocal Rank Fusion（倒数排名融合），不依赖原始分数，只依赖排名：

score(d) = Σ 1 / (k + rank_i(d))

其中 k 通常取 60，rank_i(d) 是文档 d 在第 i 路结果中的排名。

例如文档 A 在 ES 结果排第 1，在向量结果排第 5：score = 1/(60+1) + 1/(60+5) = 0.0164 + 0.0154 = 0.0318

文档 B 在 ES 排第 3，在向量排第 2：score = 1/(60+3) + 1/(60+2) = 0.0159 + 0.0161 = 0.0320

B 总分更高，排在 A 前面。RRF 的优势是不需要两路分数归一化，简单有效。

10.1 LambdaQueryWrapper 条件判空写法？

条件判空写法？
LambdaQueryWrapper wrapper = new LambdaQueryWrapper<>();
wrapper.eq(Note::getIsPublic, "1")
       .eq(Note::getStatus, "2");

// 条件判空：参数为 null 时自动跳过该条件
if (qo.getDestId() != null) {
    wrapper.eq(Note::getDestId, qo.getDestId());
}
// 链式写法更简洁：
wrapper.eq(qo.getDestId() != null, Note::getDestId, qo.getDestId());

// 排序
wrapper.orderByDesc(Note::getReleaseTime);

IPage page = new Page<>(qo.getCurrentPage(), qo.getPageSize());
noteMapper.selectPage(page, wrapper);

避免 WHERE col = NULL：如果不判空直接 .eq(Note::getDestId, null)，生成的 SQL 是 WHERE dest_id = NULL，在 SQL 中永远为 false（应该用 IS NULL）。MyBatis-Plus 的 eq(condition, column, val) 三参数重载在 condition 为 false 时自动跳过。

10.2 @TableLogic 软删除原理？

软删除实现？

实体类字段加 @TableLogic 注解：

@TableLogic
private Integer deleted;  // 0 未删除, 1 已删除

调用 removeById() 时，MyBatis-Plus 自动生成 UPDATE ta_note SET deleted=1 WHERE id=? 而非 DELETE。

所有查询自动追加 WHERE deleted=0，对业务代码透明。

10.3 分页插件原理？

PaginationInnerInterceptor 原理？

MyBatis-Plus 分页插件本质是一个 MySQL 拦截器。执行查询时：

① 先执行 SELECT COUNT(*) 查总数

② 再执行 SELECT ... LIMIT ?, ? 查分页数据

③ 包装成 IPage 对象返回（records、total、size、current、pages）

需要在配置类中注册 PaginationInnerInterceptor，项目中放在 MpConfig 类中。

面试话术：「MyBatis-Plus 中 LambdaQueryWrapper 条件判空用三参数重载 eq(condition, column, val)，condition 为 false 时自动跳过该条件，避免 WHERE col = NULL 导致索引失效。@TableLogic 软删除原理是改写 SQL 为 UPDATE SET deleted=1，查询自动追加 WHERE deleted=0，对业务代码透明。分页插件 PaginationInnerInterceptor 是 MyBatis 拦截器，先执行 COUNT 查总数再执行 LIMIT 查分页数据。」

十一、MySQL 数据库 高频

11.1 索引底层为什么用 B+ 树？

图 11.1 B+ 树结构示意图
B+ 树 vs B 树 vs 红黑树？

vs B 树：B+ 树非叶子节点不存数据，只存索引，每个节点能放更多 Key，树更矮，磁盘 I/O 更少。B+ 树叶子节点用链表连接，范围查询高效（只需遍历链表）。B 树范围查询需要中序遍历，效率低。

vs 红黑树：红黑树是二叉树，树高 = log₂N。B+ 树是多路查找树，树高 = log_m(N)，MySQL 默认 m=1200+，千万级数据树高仅 3-4 层，3-4 次磁盘 I/O 即可找到数据。红黑树千万级数据树高约 23，需要 23 次磁盘 I/O。

11.2 事务隔离级别和 MVCC？

四种隔离级别？
隔离级别脏读不可重复读幻读
READ UNCOMMITTED✓✓✓
READ COMMITTED✗✓✓
REPEATABLE READ（默认）✗✗✗（MVCC+间隙锁）
SERIALIZABLE✗✗✗

MVCC 原理：每行数据有隐藏字段 trx_id（最后修改的事务ID）和 roll_ptr（指向 undo log 版本链）。读操作通过 ReadView 判断当前事务能看到哪个版本的数据，实现读写不阻塞。

11.3 聊聊 SQL 优化经验

SQL 优化？

① 索引优化：WHERE 条件字段建索引，遵循最左前缀原则；避免索引失效（函数操作、隐式类型转换、!=、LIKE '%xxx' 左模糊）

② 避免 SELECT *：只查需要的字段，减少网络传输和内存占用

③ 分页优化：LIMIT 1000000, 10 深分页用游标 WHERE id > last_id LIMIT 10

④ 连接查询：小表驱动大表，EXPLAIN 看执行计划，确保走索引

⑤ 批量操作：用 INSERT ... VALUES (...),(...),(...) 批量插入替代循环单条插入

面试话术：「MySQL 索引用 B+ 树而非红黑树是因为 B+ 树是多路查找树，千万级数据树高仅 3-4 层，3-4 次磁盘 I/O 即可找到。非叶子节点不存数据扇出更大，叶子节点用双向链表连接范围查询高效。SQL 优化方面我遵循最左前缀原则、避免索引失效场景（函数操作、隐式类型转换、左模糊），深分页用游标 WHERE id > last_id 替代 LIMIT 1000000, 10。项目中也用 EXPLAIN 看执行计划确保走索引。」

14.2 GC 算法和垃圾回收器？

GC 算法？

基础算法：

①标记-清除：标记存活对象 → 清除未标记的。产生内存碎片。

②标记-整理：标记后把存活对象向一端移动。无碎片但慢。

③复制：把存活对象复制到另一半，清空原来的。适合存活率低的场景。

分代回收：新生代用复制算法（Eden:S0:S1 = 8:1:1），老年代用标记-整理。

常见回收器：CMS（老年代，并发标记-清除）、G1（Region 分区，可预测停顿）、ZGC（超低延迟）。

14.3 双亲委派机制？

双亲委派？

类加载时先委托父加载器加载，父加载器加载不了才自己加载。层级：BootstrapClassLoader → ExtClassLoader → AppClassLoader。

好处：① 防止核心类被篡改（自定义 java.lang.String 会被 Bootstrap 加载真正的 String）；② 避免重复加载。

打破双亲委派：Tomcat 的 WebAppClassLoader 优先加载自己 Web 应用目录下的类；SPI 机制用线程上下文类加载器加载实现类。

面试话术：「JVM 内存分为堆、方法区/元空间、虚拟机栈、本地方法栈、程序计数器。堆是对象实例存放区域也是 GC 主要区域，方法区存类信息和常量池。GC 采用分代回收——新生代用复制算法（Eden:S0:S1=8:1:1），老年代用标记-整理。双亲委派机制是类加载先委托父加载器，好处是防止核心类被篡改。Tomcat 的 WebAppClassLoader 打破了双亲委派，优先加载 Web 应用自己的类。」

十六、项目场景深度追问 高频

16.1 游记内容和主体为什么拆两张表？

ta_note 和 ta_note_content 为什么拆开？

游记内容（ta_note_content.content）是 text 大字段，可能几十 KB。游记列表只需要标题、封面、摘要等元数据，不需要内容。如果放一张表，SELECT * FROM ta_note 会把所有大字段都加载到内存，浪费 I/O 和内存。

拆分后，列表查询只查 ta_note，详情页才 JOIN 查 ta_note_content。两张表通过相同的 id 一对一关联。

16.2 冗余字段设计（dest_name、note_title）不怕数据不一致吗？

冗余字段一致性问题？

游记表中冗余了 dest_name（目的地名称），评论表冗余了 note_title（游记标题）。

接受不一致的权衡：目的地改名是极低频操作，即使冗余字段没更新，显示旧名称对用户体验影响也很小。但避免了每次查评论都要 JOIN 游记表、每次查游记都要 JOIN 目的地表的性能开销。

兜底方案：目的地改名时，可以通过消息队列异步更新所有冗余字段。

16.3 @InnerAuth 内部调用安全怎么保证的？

@InnerAuth 原理？

Feign 内部调用时在请求头加 from-source=inner。@InnerAuth 注解的方法由 InnerAuthAspect 切面拦截，检查请求头是否有 from-source=inner，没有则拒绝访问。

这样保证了 Feign 接口只能被微服务内部调用，外部用户即使知道接口地址也无法直接访问。

局限：from-source 是明文请求头，如果网关不做过滤，外部可以伪造。生产环境应在网关层过滤掉外部请求携带的 from-source 头。

16.5 递归构建商场区域树怎么做的？

树形结构构建？

目的地表用 parent_id 实现树形结构。构建区域树有两种方式：

方式一：递归查询——从根节点开始，查子节点，再递归查子节点的子节点。简单但 N+1 查询问题。

方式二：一次查全部 + 内存组装（推荐）——SELECT * FROM ta_destination 全量查出，在内存中用 Map 按 parent_id 分组，递归组装树。只需一次 DB 查询。

List all = destinationMapper.selectList(null);
Map> parentMap = all.stream()
    .collect(Collectors.groupingBy(Destination::getParentId));

// 递归组装
List buildTree(Long parentId) {
    List children = parentMap.get(parentId);
    if (children != null) {
        children.forEach(child -> 
            child.setChildren(buildTree(child.getId())));
    }
    return children;
}

18.3 volatile 的作用和原理？

volatile 两个作用？

① 保证可见性：volatile 变量写入后，JMM 会立即刷新到主内存并通知其他 CPU 缓存行失效。其他线程读取时从主内存重新加载。

② 禁止指令重排：底层用内存屏障（Memory Barrier）。在 volatile 写操作前插入 StoreStore 屏障，写操作后插入 StoreLoad 屏障，防止编译器/CPU 重排序。

不保证原子性：i++ 是读-改-写三步操作，volatile 无法保证原子性。需要 AtomicInteger（CAS）或 synchronized。

典型应用：DCL 单例模式中 private volatile static Singleton instance，防止 new 对象时指令重排（分配内存 → 赋值引用 → 初始化，重排后其他线程可能拿到未初始化的对象）。

18.4 CAS 和 AQS 原理？

CAS 原理？

CAS（Compare And Swap）：三个操作数——内存值 V、期望值 A、新值 B。当 V == A 时，将 V 改为 B，否则不做操作。整个操作是原子的（CPU 指令 cmpxchg）。

ABA 问题：线程1读到 A，线程2把 A→B→A，线程1 CAS 成功但中间值变化了。解决方案：AtomicStampedReference 加版本号。

AQS 原理？

AQS（AbstractQueuedSynchronizer）是 ReentrantLock、Semaphore、CountDownLatch 的底层框架。

核心：一个 volatile int state 表示同步状态 + 一个 CLF 双向队列存储等待线程。

独占模式（ReentrantLock）：state=0 未加锁，state=1 已加锁，state=2 重入。获取锁失败的线程包装成 Node 入队，park 阻塞。前驱节点释放锁时 unpark 后继节点。

共享模式（Semaphore/CountDownLatch）：state 表示许可数 / 倒计数。

18.5 ThreadLocal 内存泄漏问题？

ThreadLocal 为什么会内存泄漏？

ThreadLocal 的数据存在每个线程的 ThreadLocalMap 中，Key 是 ThreadLocal 对象的弱引用，Value 是强引用。

当 ThreadLocal 对象被回收后，Key 变成 null，但 Value 仍被 ThreadLocalMap 强引用。如果线程不结束（如线程池中的线程），Value 永远无法回收 → 内存泄漏。

解决方案：使用后显式调用 threadLocal.remove()。项目中用 ThreadLocal 存当前登录用户信息时，在拦截器 afterCompletion 中 remove。

18.6 ConcurrentHashMap 1.7 vs 1.8？

ConcurrentHashMap 演进？

1.7：Segment 分段锁。数组 + 链表，默认 16 个 Segment，每个 Segment 是一个独立的小 HashMap，加 ReentrantLock。并发度 = Segment 数量。

1.8：去掉 Segment，用 Node 数组 + 链表/红黑树。锁粒度细化到每个桶（数组元素）。写操作用 CAS + synchronized 锁头节点。链表长度 ≥ 8 且数组长度 ≥ 64 转红黑树。

改进原因：1.7 分段锁并发度固定，1.8 锁粒度更细，并发度 = 数组长度，性能更好。

19.3 循环依赖和三级缓存？

Spring 怎么解决循环依赖？

以 A 依赖 B，B 依赖 A 为例，Spring 用三级缓存解决：

singletonObjects（一级）：完整的单例 Bean（成品）

earlySingletonObjects（二级）：半成品 Bean（已实例化，未注入完）

singletonFactories（三级）：ObjectFactory，能提前生成 Bean 的工厂

流程：

① 创建 A，实例化后把 A 的 ObjectFactory 放入三级缓存

② A 注入 B，去创建 B

③ B 实例化后注入 A，从三级缓存拿到 A 的 ObjectFactory → 调用 getObject() 得到半成品 A → 放入二级缓存

④ B 注入半成品 A 完成，B 变成成品放入一级缓存

⑤ A 拿到成品 B，注入完成，A 变成成品放入一级缓存

三级缓存只能解决单例 setter 注入的循环依赖。构造器注入的循环依赖无法解决（实例化阶段就需要依赖），Spring 会直接报错。

19.4 @Transactional 失效的 7 种场景？

@Transactional 什么时候会失效？

① 自调用：同类中 A 方法调用 B 方法（B 上有 @Transactional），不经过代理对象，事务失效。解决：注入自己 @Autowired private XxxService self 或 AopContext.currentProxy()。

② 方法非 public：Spring 事务默认只对 public 方法生效。

③ 异常被 catch 吞掉：方法内 try-catch 了异常没抛出，Spring 感知不到异常，不回滚。

④ 异常类型不匹配：默认只回滚 RuntimeException 和 Error。抛出 checked Exception 不回滚。需 @Transactional(rollbackFor = Exception.class)。

⑤ 数据库不支持事务：MySQL 表引擎为 MyISAM 不支持事务。

⑥ 传播行为错误：PROPAGATION_NOT_SUPPORTED 以非事务方式运行。

⑦ Bean 没被 Spring 管理：类没有注解 @Service/@Component，不是 Spring Bean，代理不生效。

项目中游记发布用 @Transactional 保证 ta_note 和 ta_note_content 两表写入的原子性。面试时提到"如果 Controller 直接调 Service 内部方法，没走代理就会失效"，体现对 AOP 代理的理解。

20.1 Redis 分布式锁怎么实现？SETNX 有什么问题？

Redis 分布式锁方案？

基础方案：SET lock_key uuid NX EX 30（原子加锁 + 过期时间）。释放锁用 Lua 脚本判断 uuid 一致才删除（防止删别人的锁）。

-- 释放锁 Lua 脚本
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end

SETNX 的两个问题：

① 锁过期但业务未完成：线程 A 获得锁，执行 35 秒，但锁 30 秒就过期了。线程 B 拿到锁，此时 A 和 B 都在执行 → 并发问题。

② 误删别人的锁：A 锁过期后 B 获得锁，A 执行完后 DEL 删掉了 B 的锁。→ 用 uuid + Lua 解决。

Redisson 怎么解决锁过期问题？

看门狗（Watchdog）机制：Redisson 加锁时默认 30 秒 TTL，后台启动一个守护线程，每隔 10 秒（TTL/3）检查：如果线程还持有锁，就续期到 30 秒。

可重入：Redisson 用 Hash 结构存储，Key 是锁名，Field 是线程 ID，Value 是重入次数。同一线程再次加锁 Value+1，释放 Value-1，减到 0 删除 Key。

项目应用：秒杀场景也可以用 Redisson 分布式锁 RLock.lock() 替代 Lua 脚本，但性能略低（多一次续期线程开销）。

22.1 Docker 核心概念：镜像、容器、仓库

图 22.1 Docker 镜像-容器-仓库关系与生命周期
Docker 三个核心概念？

镜像（Image）：只读模板，包含运行应用所需的所有内容——代码、运行时、库、环境变量、配置文件。类似面向对象中的"类"。镜像采用分层存储（UnionFS），每条 Dockerfile 指令生成一层，层与层之间可复用。

容器（Container）：镜像的运行实例，可以启动、停止、删除。类似面向对象中的"对象"。每个容器相互隔离，拥有自己的文件系统、网络、进程空间。容器在镜像顶层增加一个可写层（Copy-on-Write），删除容器后可写层数据丢失。

仓库（Registry）：存储和分发镜像的服务。Docker Hub 是最大的公共仓库；企业搭建私有仓库（Harbor）存放内部镜像。通过 docker push 上传、docker pull 下载。

23.1 SpringBoot 自动配置原理是什么？

图 23.1 SpringBoot 自动配置原理流程
SpringBoot 自动配置原理？

入口：@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。

核心流程：

① @EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 导入选择器。

② 选择器调用 SpringFactoriesLoader.loadFactoryNames()，读取 classpath 下所有 jar 包的 META-INF/spring.factories 文件（SpringBoot 2.x），或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（SpringBoot 3.x）。

③ 获取到 100+ 个自动配置类的全限定名，逐个加载。

④ 每个配置类上有 @Conditional 系列注解做条件过滤：

  @ConditionalOnClass：classpath 中存在指定类才生效（如引入了 Redis 依赖，RedisAutoConfiguration 才生效）。

  @ConditionalOnMissingBean：容器中没有该类型 Bean 才生效（用户自定义的 Bean 优先于默认配置）。

  @ConditionalOnProperty：配置文件中指定属性满足条件才生效。

⑤ 条件满足的配置类被注册到容器，其中的 @Bean 方法创建 Bean。

一句话总结：SpringBoot 自动配置 = 从 spring.factories 加载配置类 + @Conditional 条件过滤 + 用户 Bean 优先。

24.2 Spring Boot 怎么集成 WebSocket？

Spring Boot WebSocket 集成方式？

方式一：原生 WebSocket（@ServerEndpoint）

@Component
@ServerEndpoint("/ws/parking/{parkingId}")
public class ParkingWebSocket {
    private static ConcurrentHashMap clients = new ConcurrentHashMap<>();

    @OnOpen
    public void onOpen(Session session, @PathParam("parkingId") String parkingId) {
        clients.put(parkingId, session);
    }

    @OnMessage
    public void onMessage(String message, Session session) {
        // 处理客户端消息
    }

    @OnClose
    public void onClose(@PathParam("parkingId") String parkingId) {
        clients.remove(parkingId);
    }

    // 服务端主动推送
    public static void sendToClient(String parkingId, String message) {
        Session session = clients.get(parkingId);
        if (session != null && session.isOpen()) {
            session.getAsyncRemote().sendText(message);
        }
    }
}

25.1 数据库连接池原理

图 25.1 数据库连接池原理
为什么需要数据库连接池？

没有连接池时，每次数据库操作都要经历：TCP 三次握手 → MySQL 认证 → 执行 SQL → MySQL 断开 → TCP 四次挥手。建连和断开的开销远大于 SQL 执行本身。

连接池在应用启动时预创建一批连接放入"池"中，业务线程用时从池中"借"一个，用完"还"回去复用。避免重复建连，大幅降低延迟和资源消耗。

核心参数：

① initialSize：初始连接数，启动时预创建。

② maxActive：最大连接数，保护数据库不被打满。

③ maxWait：获取连接超时时间，超时抛异常，防止线程无限等待。

④ minIdle：最小空闲连接数，保证一定量的热连接随时可用。

26.1 Quartz 核心三要素

图 26.1 Quartz 三要素关系
Quartz 核心三要素？

Job（任务）：实现 Job 接口，重写 execute() 方法，里面写具体业务逻辑。是一个被调度执行的任务。

Trigger（触发器）：定义 Job 何时执行、执行多少次。两种主要类型：

26.3 使用场景：趣谷集计数批量回写数据库

项目中 Quartz 怎么用的？

业务场景：趣谷集项目中，游记的浏览量、点赞数、收藏数、评论数存在 Redis Hash 中（HINCRBY 原子递增）。如果每次点赞都直接写 MySQL，高频操作会给 DB 带来巨大压力。

方案：用 Quartz 定时任务每隔 5 分钟将 Redis 中的计数批量回写到 MySQL。

@Component
public class NoteStatsSyncJob implements Job {
    @Autowired
    private NoteStatsService statsService;
    @Autowired
    private RedisService redisService;

    @Override
    public void execute(JobExecutionContext context) {
        // 1. 扫描所有 note:stats:* 的 Key
        Set keys = redisService.keys("note:stats:*");
        if (keys == null || keys.isEmpty()) return;

        // 2. 批量读取 Redis 计数
        List batchList = new ArrayList<>();
        for (String key : keys) {
            Map stats = redisService.hGetAll(key);
            Long noteId = Long.parseLong(key.split(":")[2]);
            NoteStats ns = new NoteStats();
            ns.setId(noteId);
            ns.setViewnum(Integer.parseInt(stats.get("viewnum").toString()));
            ns.setThumbsupnum(Integer.parseInt(stats.get("thumbsupnum").toString()));
            // ...
            batchList.add(ns);
        }

        // 3. 批量 UPDATE 到 MySQL
        statsService.batchUpdate(batchList);
        log.info("计数回写完成, 共 {} 条", batchList.size());
    }
}

// Cron: 0 0/5 * * * ? → 每 5 分钟执行一次

为什么用 Quartz 而非 Spring @Scheduled：Quartz 支持集群部署——多个服务实例同时运行定时任务时，Quartz 通过数据库锁保证只有一个实例执行，避免重复执行。@Scheduled 在集群环境每个实例都会执行，需额外加分布式锁。

刷库策略选择：5 分钟是权衡值——太频繁（如 10 秒）失去缓冲意义，太长（如 1 小时）宕机时数据丢失风险大。Redis 持久化 AOF 保证 5 分钟内的数据可靠性。

面试话术：「趣谷集项目的浏览量、点赞数等高频计数，我用 Redis Hash + HINCRBY 原子递增，但不可能每次点赞都写 MySQL。用 Quartz 定时任务每 5 分钟扫描 Redis 中的 note:stats:* Key，批量回写到数据库。选 Quartz 而非 Spring @Scheduled 的原因是：微服务多实例部署时，Quartz 通过数据库行锁保证只有一个实例执行定时任务，避免重复执行。5 分钟的间隔是权衡——太频繁失去缓冲意义，太长宕机时丢数据多，配合 Redis AOF 持久化保证数据不丢。」

27.1 TCP 三次握手与四次挥手

图 27.1 TCP 三次握手与四次挥手
为什么是三次握手，不是两次或四次？

两次不够：如果只有两次（客户端 SYN → 服务端 SYN+ACK），服务端发出 SYN+ACK 就认为连接建立了。但这个包可能丢在网络上，客户端没收到，服务端却在等数据——浪费资源。

三次足够：第三次握手（客户端 ACK）让服务端确认"客户端收到了我的 SYN+ACK"，双方都知道彼此收发能力正常。三次是确认双方收发能力的最小次数。

四次多余：三次已经达成双向确认，第四次没有额外信息。

为什么挥手是四次而握手是三次？

握手时 SYN+ACK 可以合并成一个包发送（服务端没有已建立的数据需要处理）。挥手时，服务端收到客户端 FIN 后，可能还有剩余数据没发完，所以先回 ACK（"我知道你要关了"），等数据发完再发 FIN（"我也准备关了"）。ACK 和 FIN 不能合并，所以是四次。

TIME_WAIT 状态：客户端最后发完 ACK 后进入 TIME_WAIT，等待 2MSL（最大报文生存时间）才真正关闭。原因：① 确保服务端收到最后的 ACK（如果丢了，服务端会重发 FIN，客户端还能响应）；② 让本次连接的残留报文在网络中消失，避免影响新连接。

27.3 从浏览器输入 URL 到页面显示的完整过程

浏览器输入 URL 发生了什么？

① DNS 解析：浏览器缓存 → 操作系统 hosts 文件 → 本地 DNS 服务器 → 根域名服务器 → 顶级域名服务器 → 权威域名服务器，最终拿到 IP 地址。

② TCP 三次握手：浏览器与服务器建立 TCP 连接。

③ TLS 握手（HTTPS）：协商加密算法、验证证书、交换密钥。

④ 发送 HTTP 请求：构造 HTTP 请求报文（Method、URL、Headers、Body），发送给服务器。

⑤ 服务器处理并响应：经过 Gateway → Controller → Service → Mapper → DB → 返回 HTTP 响应（Status Code、Headers、Body）。

⑥ 浏览器渲染：解析 HTML → 构建 DOM 树 → 解析 CSS → 构建 CSSOM → 合并成 Render 树 → Layout 布局 → Paint 绘制 → Display。

⑦ 连接断开：TCP 四次挥手（如果 Connection: close）。

面试话术：「TCP 三次握手的本质是确认双方的收发能力——第一次握手服务端确认客户端能发，第二次握手客户端确认服务端能收能发，第三次握手服务端确认客户端能收，三次之后双向通道就建立好了。四次挥手比握手多一次是因为 TCP 是全双工的，服务端收到 FIN 后可能还有数据没发完，需要先 ACK 再单独发 FIN。我在项目中 Gateway 到下游微服务的 HTTP 调用、Feign 的跨服务调用底层都是 TCP 连接，连接复用通过连接池管理避免频繁握手。」

28.2 死锁的产生条件和预防

什么是死锁？怎么预防？

死锁定义：两个或多个线程互相等待对方释放资源，导致所有线程都无法继续执行。

死锁四个必要条件（全部满足才发生）：

① 互斥：资源同一时刻只能被一个线程占用。

② 请求与保持：线程持有资源的同时还在请求新资源，不释放已持有的。

③ 不剥夺：资源不能被强制夺走，只能等持有者主动释放。

④ 循环等待：存在线程的循环等待链（A 等 B 的资源，B 等 A 的资源）。

预防策略（破坏其中一个条件）：

① 破坏请求与保持：一次性申请所有资源（执行前获取全部锁）。

② 破坏循环等待：对锁排序，所有线程按相同顺序获取锁。

③ 破坏不剥夺：用 tryLock(timeout) 超时放弃，释放已持有的锁重试。

项目中的关联：Java 的 synchronized 不可中断（不剥夺），如果嵌套 synchronized 容易死锁。用 ReentrantLock 的 tryLock() 可以避免死锁。分布式场景下，Redis 分布式锁加超时时间也是防死锁。
